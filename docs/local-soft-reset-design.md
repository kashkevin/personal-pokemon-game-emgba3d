# Personal encounter reset foundation

This design implements the [owner's Local Soft Reset amendment](project-update-local-soft-reset.txt) through an explicit native personal-encounter boundary. It does not reboot a core, restore an emulator savestate, import an older checkpoint, or change another character. The first implementation slice is deliberately a **first-action-only development capability**. Two-core and four-core exploration proofs passed; later turns, production encounter coverage, durable attempts across crashes, Windows chord routing and the simultaneous trade/battle/reset matrix remain required work.

## Why an explicit script boundary is necessary

In the pinned `data/maps/SkyPillar_Top/scripts.inc`, Rayquaza is generated after its cry and delay, then the script starts the legendary battle. On return it distinguishes won, ran and teleported outcomes; the remaining path sets `FLAG_DEFEATED_RAYQUAZA`. Run/teleport paths also remove the object. Calling the recorded-battle quit helper or assigning an ordinary battle outcome without an earlier reset branch can therefore hide or defeat the intended hunt target. The map's resume handler also observes `FLAG_SYS_CTRL_OBJ_DELETE` and the caught outcome. [Audited script](https://github.com/rh-hideout/pokeemerald-expansion/blob/bb1093a7c72d3961d9a37d8e02ad2abc2c866682/data/maps/SkyPillar_Top/scripts.inc)

Each supported encounter needs a compiled descriptor tied to its exact map, object/script, species and ordinary prerequisites. The descriptor begins immediately before native generation and has an explicit reset-return branch before any defeat, hide, reward or capture progression. Unlisted static scripts, ordinary grass/fishing encounters, gifts, roaming encounters, trainer/PvP/link battles and World Events are ineligible until separately audited. An event must use its immutable assigned identity/properties and must never enter the personal reroll context.

## Initial native lifecycle

The isolated `engine-local-reset` worktree starts at `54f977f`. New `multiplayer_local_reset.c/.h` owns the descriptor, a monotonic runtime generation, its state and a bounded guard copy. The copy is only compared to current native data; it is never restored as a character snapshot.

1. An explicitly enabled development script offers a reachable personal/static test encounter through ordinary interaction. The normal shipping build has this probe disabled. It does not unlock the story, add a normal wild Legendary, or establish production Rayquaza eligibility.
2. Native entry verifies the descriptor, player party, current enrollment/lifecycle state and prerequisites. It records the player's party/count, bag, money/coins and relevant capture/progression state. The ordinary generator creates the enemy from the requesting core's live RNG. Starting the encounter increments its informational development counter once.
3. The reset window opens only while the native player controller is waiting at the first action-selection menu, before an action or item selection. It also requires unchanged protected native state. Entry effects that consume an item, alter the party, or otherwise violate that condition cause refusal rather than a rollback.
4. A reset request can present native Yes/No confirmation. No/B leaves the current enemy roll and counter intact. Confirming Yes rechecks the exact same generation, source, state and guards. Accepting any ordinary battle action closes the reset window; cancellation of a later submenu does not silently reopen it. Capture transfer is additionally fenced at the native caught-mon path.
5. The reset performs ordinary native fade/resource cleanup, bypasses persistent postbattle side effects applicable to completed battles, and returns to the authored reset branch. The object and prerequisite flags remain intact. The next ordinary interaction creates a fresh native roll and increments the counter; the reset button alone does neither.

The source seams are the main input/reset branch, first `HandleInputChooseAction`, the native capture transfer, and the scripted-wild return callback. Cleanup must not accidentally apply toxic-status downgrade, pickup/reward processing, EXP or a defeat branch to an aborted first-action encounter. Tests must inspect actual party/inventory bytes before and after this path. The new native status/helper must distinguish an active enrollment from an unsafe save, trade or battle hold; a pending ownership operation cannot be dismissed by resetting.

The development counter uses explicitly audited unused persistent vars with bounded overflow behavior and a version/magic check. It is preserved by ordinary Save and the existing full character checkpoint. It is **not yet crash-durable before the next save** and is not the eventual per-static statistics catalogue. No save-layout migration or new canonical store schema is claimed by this slice. The final system needs idempotent durable attempt IDs and a defined interruption boundary so retries neither invent attempts nor discard a committed capture. That design must be settled before counters receive complete persistence acceptance.

## Gen 6 shiny generation audit

Both the pinned engine and inspected current upstream define `SHINY_ODDS` as 8 out of 65,536. Changing `GEN_LATEST` does not alter this separate constant. The current engine's stored shiny interpretation is its PID/OT xor predicate combined with `BoxPokemon.shinyModifier`. Changing the global threshold to 16 would change some existing stored Pokémon with xor values 8–15, including owned Pokémon. Existing shiny status must remain preserved. [Current constant](https://github.com/rh-hideout/pokeemerald-expansion/blob/6057b187f946094d614e9c34bc12731ea6a5b7bb/include/constants/pokemon.h)

PKHeX's reviewed Gen 6 format code compares Trainer/Pokémon shiny values after shifting their xor by four bits, while its common shiny predicate tests equality. This is equivalent to the 16-value Gen 6 shiny range; for a uniform 16-bit shiny xor its base probability is 16/65,536, or 1/4,096. That probability is an inference from the primary format implementation, not a new balance selection. Reviewed revision `66ef5983a5d349efa2dd615f2926a1b1ee97306e`. [Gen 6 values](https://github.com/kwsch/PKHeX/blob/66ef5983a5d349efa2dd615f2926a1b1ee97306e/PKHeX.Core/PKM/Shared/G6PKM.cs), [common predicate](https://github.com/kwsch/PKHeX/blob/66ef5983a5d349efa2dd615f2926a1b1ee97306e/PKHeX.Core/PKM/PKM.cs)

A proposed later generation-only personal threshold can reuse the native `MON_DATA_IS_SHINY` setter, which stores the chosen result relative to the existing serialization/display predicate. It can implement Gen 6 new rolls while preserving stored Pokémon. That source-aware change needs separate review before C implementation; the first reset slice does not silently switch global odds or claim the completed Gen 6 encounter profile.

The existing `ComputePlayerShinyOdds` combines Charm, lure, chain-fishing and DexNav bonuses. Current upstream's Charm setting is two additional rolls; the pinned fishing chain and DexNav are disabled, but a lure's remaining steps can still affect this generic generation function. A personal static context must not inherit unrelated fishing/lure/DexNav state. Force-shiny/no-shiny flags and scripted preset/event identities need explicit source handling. Keep ordinary wild paths intact during the first reset implementation. The future Charm must use only the requesting player's legitimate item, and event generation must bypass personal modifiers. Charm purchase, price and any encounter-specific exceptions remain separate work. [Generation hook](https://github.com/rh-hideout/pokeemerald-expansion/blob/6057b187f946094d614e9c34bc12731ea6a5b7bb/src/pokemon.c), [Charm configuration](https://github.com/rh-hideout/pokeemerald-expansion/blob/6057b187f946094d614e9c34bc12731ea6a5b7bb/include/config/item.h)

## Input and actual proof

The current Windows SDL adapter suppresses Start from the full A+B+Select+Start combination and blocks frontend resets. Native main currently invokes BIOS reset for that raw chord. A qualified native handler can consume it once per release and refuse it outside an eligible connected encounter, but the Windows adapter must later route the request deliberately. A headless joypad proof does not establish Windows chord acceptance. An explicit in-game action is a valid first input path; confirmation must consume its button presses before normal action selection.

The first actual proof uses fresh private copies, ordinary NPC interaction and joypad input, official core framebuffer/Flash diagnostics and the production bridge. No RAM/save injection, teleport, savestate or story-flag editing is allowed. It must demonstrate repeated visible encounters and fresh native PID/IV rolls, exact counter increments, No/B cancellation, ordinary Save and fresh Continue, persistent capture followed by a durable ownership checkpoint, and refusal to reset after capture/action or during another ownership lifecycle. Same core PID, connection, player lease and incarnation remain intact through successful local resets.

For independent-player coverage, other actual cores must keep advancing on independent maps while their canonical heads and native identities remain intact. Subsequent four-player scenarios combine the hunt with a real trade between two other players and a local battle, then repeat with a wild encounter. This accounts for the fact that a two-person trade occupies two of the three nonrequesting players. Full simultaneous combat/trade/reset acceptance waits for the corresponding native battle/trade capabilities; menus or synthetic traffic cannot substitute for it.

World Events are not yet implemented, so the first slice can prove source-based refusal with a dedicated negative descriptor and native tests. It cannot claim that a nonexistent production event engine has passed immutable-event recovery. Disconnect, changed lease/incarnation, server restart and unknown outcomes must require reconciliation before another reroll. General offline play is not selected by this design.

Frozen engine `071af0af967578fd1c457fdd5da27e0de44e395b` provides a default-off Littleroot Boy test interaction that generates a personal level-3 Wurmple. It has not yet been merged with native singles/Multi.

The engine's annotated `LOCAL_RESET_DEV_POC` tag pins this source and its bounded development acceptance. It does not qualify production static encounters, Windows input or the combined native battle/reset build.

`local-reset-run-7` passed 19 checks in two actual cores. `local-reset-four-run-1` then passed 21 checks with four distinct original trainers. Ordinary NPC/joypad interaction verified the visible reset prompt, No preserving the enemy and counter, Yes returning through native cleanup, and a second entry producing a different native PID/IV roll while incrementing the attempt counter from 1 to 2. Choosing a normal action permanently refused reset for that encounter. An ordinary ball capture obtained the second Wurmple, assigned ownership serial 3 and locked the encounter against another reset. No runtime memory or save injection was used.

Ordinary Save persisted counter 2 and the captured flag. Canonical checkpoint, live recovery, a further checkpoint and fresh Continue retained the three owned Pokémon and capture identity. B and C kept moving; D was on another map with its menu open. All three nonrequesting canonical heads remained at revision 1, and the reset checks retained all four core identities, leases and incarnations. All eight original/fresh core processes closed, original source hashes remained unchanged and SQLite integrity passed. A lost development terminal handle was recovered only to submit the proof's final `finish` command; the cores and world were not restarted to complete that run.
