# Windows launcher and game import

`src/emerald_multiplayer/launcher_gui.py` provides visible Host Game and Join Game tabs over `LauncherSession`. Normal play opens existing worlds and enrolled characters. The separate setup window creates a private world, prepares a fresh ordinary character, explicitly approves/enrolls a source, and exports individual friend invitations. The main window exposes world/invitation file selection and a local host address, with an explicit Internet setting. It does not expose developer credentials, receipt endpoints, runtime paths or release hashes. Invitations remain private files.

The session worker owns one asyncio loop on a background thread. Tk widgets are updated only on the creating thread through a queue of fixed status codes. Host/Join actions cannot overlap. Cancel startup waits for context cleanup; repeated cancellation does not interrupt that cleanup. Closing the launcher during play asks the player to close the game window, then waits for child/session cleanup. This does not select the pending disconnect or interrupted-battle policy. A connection change is displayed without silently terminating, reconnecting or merging progress.

Application entry points supply `LauncherRelease` pins; arbitrary installation files and invitations cannot select them. Per-user game files live under `%LOCALAPPDATA%/PokemonPrivate/launcher/games/<ROM SHA-256>/game.gba`. No current-directory storage fallback exists. Running the module without a compiled release displays a disabled development preview.

## Explicit Save now

The main window exposes **Save now** while its owned game is running. This uses the existing `LiveCheckpointCoordinator` and native safe-point export, canonical host commit and verified release. It never writes the live save file. The first expected revision comes from verified cold startup; later revisions advance only after a complete matching export receipt. A missing bridge or definite native safe-point rejection permits another explicit click. An uncertain result, changed bridge/session or invalid receipt requires recovery and disables further saves in that session. There is no automatic retry or adoption of a newer server head.

Only one save may run. Game closure and repeated caller cancellation drain an already dispatched operation while the runtime still owns the character's file lease; transports and storage close afterward. Closing the game does not implicitly save. Automatic intervals, offline continuation and interrupted-battle settlement remain pending decisions. Later in-session trades or battles that advance a checkpoint must pass their verified local completion receipt into the launcher's revision tracking before this controller can continue saving; querying a new head alone is insufficient.

Six Windows save-controller cases pass, alongside the existing twenty session and thirteen GUI/worker cases. They exercise real TLS, SQLite, owned startup, a real stand-in child process and file leases; only the native exporter completion is simulated. The first run caught an inaccurate fixture that copied a closed save's RTC trailer size into native export metadata. Correcting the fixture to native Flash size made all six pass without weakening production validation. Actual Windows native export and packaged button acceptance remain separate evidence.

The same 26 save/session cases pass on WSL with zero skips in 85.398 seconds. The private Windows original/recheck and WSL logs are retained; the WSL log was copied and hash-verified into the physical Windows private archive.

## Explicit setup flow

`launcher_setup_gui.py` composes the [public setup controller](launcher-setup.md). A new world accepts one host and at most three friend names, a numeric invitation endpoint and a port. Each friend invitation is exported independently to a new file; the private host descriptor is never exported as a friend invitation. World creation does not enroll any character.

The host may select an original saved character or prepare one through `DraftRuntime`: ordinary New Game, starter selection, native Save, then natural game-window closure. A validated draft receipt is selected only after the private draft context and lease have closed. No synthetic save or injected story/party state is used. The approval checkbox is cleared when the world, source or selected character changes. The explicit approval/open action launches `EnrollmentRuntime`; the player uses ordinary Continue and explicitly presses Finish enrollment at a safe field point. That context closes before normal `LauncherSession`/cold recovery can start. Closing setup drains its worker/child before closing either window. No setup operation grants a remote-registration capability or selects the pending disconnect/battle policy.

## Connection check and acceptance limits

Join Game's **Check connection** uses `network_diagnostics.probe_invitation`. It validates the invitation, connects only to that numeric invited endpoint with a bounded timeout, checks the exact TLS certificate using the existing dedicated trust implementation, then closes without sending any application bytes. It never sends the player credential, joins a world, replaces another connection, changes system trust, or configures an adapter, router or firewall. The developer CLI is `scripts/windows-runtime/check_connection.py <invitation>`.

Results distinguish a loopback, LAN or public address from an actual path test. Even a successful public-address probe from the host may use router hairpin routing. Every result explicitly keeps `player_authenticated`, `separate_device_proven` and `internet_path_proven` false. Another PC's gameplay and an outside-network gameplay session remain necessary acceptance checks.

Read-only adapter inspection on the development PC found a usable Ethernet LAN address, a link-local Wi-Fi address, and an existing VPN interface. No adapter or firewall setting was changed. Therefore a same-PC Ethernet-address probe would not establish a Wi-Fi or separate-PC connection. Real TLS loopback fixtures verify that the server receives EOF with zero application bytes; refused connections and invalid invitations return bounded statuses without credentials.

## Reuse review, October 8, 2026

| Component | Review and decision |
| --- | --- |
| Existing project runtime | Reuse `LauncherSession`, `GameInstallation`, `RuntimeBundle`, host invitations and the qualified SDL runtime. GUI code adds no alternate native launch or recovery route. |
| Python/Tk | Installed Windows Python 3.14.4 includes Tcl/Tk 8.6. Reuse stdlib `tkinter.ttk`; no additional GUI library is incorporated. The official [Tkinter documentation](https://docs.python.org/3/library/tkinter.html) describes its event loop and thread constraints. Keep network/recovery work outside Tk handlers. Python has [PSF notices](https://docs.python.org/3/license.html), and Tcl/Tk has [permissive license terms](https://www.tcl-lang.org/software/tcltk/license.html); packaged copies must retain relevant notices. |
| Qt/PySide alternative | The official [PyInstaller deployment guidance](https://doc.qt.io/qtforpython-6/deployment/deployment-pyinstaller.html) establishes a compatible alternative. This two-tab window does not justify adding another GUI runtime alongside the existing SDL game frontend. No Qt source is incorporated. |
| PyInstaller | Official [operation documentation](https://pyinstaller.org/en/stable/operating-mode.html) supports bundling the interpreter and Tk into a Windows application. Use a Windows `onedir`, windowed build before considering one-file mode. Its [license exception](https://pyinstaller.org/en/stable/license.html) permits application bundling subject to included dependency licenses. The executable still requires clean-machine qualification; build success is insufficient. |
| BPS import | Existing project delivery requires an owner's dump plus input/output verification. [byuu's public-domain format specification](https://github.com/Sir-Walrus/Flips/blob/master/bps_spec.md) covers the four commands and CRC footer. The archived Flips project is a potential developer patch generator, not a maintained runtime dependency. [RomPatcher.js](https://github.com/marcrobledo/RomPatcher.js/tree/3183884086825c3a57c72026234debcef1e2240c) supplies an MIT browser/Node implementation, but embedding JavaScript would add another runtime and still require strict release pinning and bounds. A small bounded Python reader is being integrated against the format, without copying either project's implementation. |

Research references are not incorporated dependencies. The pinned engine and SDL runtime audit remain in [Windows runtime](windows-runtime.md) and [customization/reuse](customization-and-reuse.md). These changes do not alter engine saves or multiplayer ABI.

## Verification and remaining acceptance

The latest scoped Windows results cover twelve GUI/worker cases, seven setup GUI/worker cases, three real TLS probe cases and nine BPS/import cases, with real Tk widgets and no display skips. They cover host/join option isolation, one-worker admission, cancellation waiting for cleanup, ordinary game closure, enrollment gating, sanitized error/status messages, passive connection observation, compiled release pins and disabled preview controls. Setup tests verify receipt selection after draft context closure and a native safe-to-retry rejection that keeps the same child/context open until a second explicit Finish action. All other enrollment errors close and preserve recovery files. Session/draft behavior uses controlled lifecycle doubles; this is not native gameplay acceptance.

`game_import.py` supports all four BPS commands, signed relative offsets and overlapping target copies. It rejects corrupt CRCs, out-of-bounds reads/writes, truncated/trailing commands, excessive integers, metadata and action counts. ROM/output size is capped at 32 MiB and patch size at 64 MiB. Metadata is inert. `GameImporter` separately checks package-supplied SHA-256 pins for original dump, patch and reconstructed output. It writes a complete private temporary file, flushes it, publishes it without overwriting an existing file, and removes its own temporary file. The original dump is never modified. Fixtures use synthetic bytes, including a 2 MiB overlap run; no real base dump or release patch was available for full-game import acceptance.

## Actual standalone package preview

`scripts/windows-runtime/build_launcher.py` builds a Windows `onedir` package using the exact wheel hashes in `requirements-launcher-build.txt` plus the existing host provisioning pins. It requires explicit trusted ROM/manifest/runtime hashes, verifies all inputs and freezes Python sources before PyInstaller analysis. Only verified runtime manifest entries are copied. Python, Tk and dependency notices accompany the existing native runtime source/relink material. A new private output directory outside the repository is mandatory. No ROM, save, world database, certificate or invitation enters the package. Every resulting file is hashed.

Optional import requires all four developer inputs: `--base`, `--base-sha256`, `--patch` and `--patch-sha256`. The builder must reconstruct the pinned output before enabling the own-dump chooser. Without them it builds a development package with import visibly disabled and an explicit missing-patch notice. No fabricated patch or inferred base hash is substituted. Documented setup/source records and private baseline/runtime build artifacts contain compiled expansion builds, not an owner-supplied original dump.

## Windows keyboard qualification in progress

A subsequent package-2 check privately installed the exact verified trade game and opened an ordinary draft through the visible setup button. The native title/intro animated, and clicking its standard title-bar Close ended the child normally. The untouched 128 KiB blank Flash draft was retained without a receipt or selected enrollment source. Documented keyboard input through the computer-use helper did not advance that game; the same helper could close the idle Tk setup with Alt+F4. This is an unresolved input qualification issue, not proof that hardware keyboard input fails. No save, emulated RAM, input helper, or qualified binary was modified to work around it.

The independent SDL 2.32.10 `test/checkkeys.c` observer was built from the retained official source and the same pinned SDL DLL. A diagnostic copy added only a public SDL logging callback so its existing messages could be captured. With no game or launcher open, documented helper `x` produced `SDL_TEXTINPUT` but no keydown/up; `Return` produced no additional event; Ctrl+F produced only Left Ctrl keydown/up. The SDL event source maps most ordinary keys using Windows scan codes, with special virtual-key fallbacks for some keys. Missing scan-code delivery is consistent with these observations, but the underlying Windows message fields were not captured. Hardware keyboard behavior remains unproven. Both observer windows were closed through their standard Close buttons; no input adapter change or custom input injector was introduced. Private source, executable and event-log hashes are archived in `artifacts/windows-runtime/sdl-keyboard-diagnostic-1/diagnostic-evidence.json`.
