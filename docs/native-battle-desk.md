# Development native battle lifecycle

`BattleDesk` is a session-local consent and lifecycle service for [ABI2 native singles](native-singles-prototype.md) and the [ABI3 four-trainer, full-party Multi contract](native-battle-transport.md). It reuses the authenticated ownership store, immutable `CanonicalBattler` descriptors, and existing native mailbox codecs. The native engine and its link/controller seams remain the battle implementation; Python does not calculate moves, damage, rewards or a winner. The reuse audit and pinned source references are in [battle-transport-design.md](battle-transport-design.md).

This component has no network endpoint, ROM command executor or player menu. It writes no checkpoint, statistic, currency or reward. Its tests use genuine encrypted Flash fixtures and real SQLite heads with simulated correlated native receipts. Actual-ROM battle acceptance, controller routing, durable battle recovery and player-facing integration remain separate gates.

## Admission and consent

Construct `BattleDesk(store, lease_for, timeout=180, clock=time.monotonic)` with an explicit ownership store and the server's current connected-lease lookup. Authentication supplies each actor and lease; request bodies must never choose them. Up to two independent singles lifecycles or one four-person Multi lifecycle may occupy the four players. An unresolved native hold retains every participant's busy slot. Terminal history is bounded to 64 challenges.

`invite(actor, lease, peer, battle_id)` captures both current canonical checkpoint revisions and full-container hashes, assigns fixed source slots by sorted player UUID, and issues one immutable generation and nonzero 16-byte RNG state. `invite_multi(actor, lease, teammate, opponents, battle_id)` requires four distinct trainers and an exact two-opponent tuple. It sorts each proposed duo and interleaves their source slots, fixing the teams to 0/2 and 1/3. Each participant retains its own canonical six-slot party. This roster does not change or require persistent `TeamDesk` membership.

The sender consents only for itself. `accept(actor, lease, battle_id, generation, fingerprint)` records that actor's consent to the exact challenge; the proposed teammate must accept independently, as must both opponents. Multi uses a distinct consent-hash domain from singles. Exact retries preserve the roster, generation and RNG; changing teams or format under the same battle ID is a conflict. All participants must accept before registration. Edited heads, disconnected leases, deadline expiration or replaced registered incarnations invalidate preparation. Neither a timeout nor a disconnect declares a forfeit.

Every player needs an acknowledged owned canonical checkpoint. The native PREPARE gate must still compare its actual live six-slot party, native counter and trainer identity with that descriptor; a server snapshot alone is insufficient. Pending committed trade recovery blocks admission. The [server adapter](native-battle-arbitration.md) additionally prevents overlapping live checkpoint, trade and battle holds before dispatching commands.

## Trusted coordinator sequence

All participant methods below take `(actor, lease, battle_id, generation, ...)`, except `status(actor, lease, battle_id)`. `descriptor(...)` returns only that actor's immutable canonical material to the trusted coordinator. Public status contains revisions, hashes, readiness and lifecycle state, without party bytes, trainer bytes or the issued RNG.

1. Call `register(..., incarnation)` for every actual bridge: both in singles, all four in Multi. All registrations must exist before binding. Call `authorize_bind(...)` **before** each BIND dispatch; it records possible native hold ownership even if the reply is lost. Pass the exact request and response to `bound(..., request, response)`.
2. Obtain `preparation(...)`, dispatch PREPARE, assemble the native TRAINER block, then call `prepared(..., request, response, trainer28)`. It requires the issued preparation bytes and exact canonical trainer descriptor. PREPARE emits TRAINER only; it does not emit the full party.
3. Call trusted `authorize_start(battle_id, generation)` only after every participant has consented, bound and prepared. This marks STARTING before any dispatch, so an uncertain START cannot become an ordinary pre-start cancellation. Register each correlated START acknowledgment with `started(..., request, response)`.
4. The native startup subsequently emits the three original PARTY blocks. Call `verify_startup(..., kind, block_sequence, bytes200)` in exact order for each actor. Every byte, including unused six-slot party tails, must match its canonical descriptor. Exact retransmission is observational; changed retransmission or a skipped block requires recovery.
5. The trusted router separately validates all HEADER/RNG/startup ordering and native controller roles. Only then may it call `authorize_running(battle_id, generation)`. That method independently requires every START acknowledgment and every complete canonical party, including all three PARTY blocks from the fourth trainer in Multi. Ordinary client requests cannot invoke either authorization hook.
6. Native KEEP receipts may be submitted with `keepalive(..., request, response)`. A new successful receipt extends the service deadline; an exact old receipt does not. KEEP cannot revive an expired, aborting or recovery-required lifecycle.
7. Call `finish(..., query_request, query_response, outcome=..., party=bytes600, party_count=...)` only after native restoration. The native query must still be held, started and restored, with the exact revision and normalized fixed-side outcome: 1 for the even-slot side, 2 for the odd-slot side, 3 for a draw. Every actor must provide equal outcomes and its exact original party/count. Multi remains FINISHING until all four agree; one conflicting result requires recovery. These receipts authorize release; they do not close the lifecycle.
8. Dispatch native RELEASE with each actor's verified original-party CRC and agreed outcome. `released(..., request, response)` closes only after every exact successful acknowledgment. Three Multi releases leave the lifecycle open. The standalone Desk tolerates a later head advancement for an already released actor without stranding the remaining release receipts; the server adapter still blocks all participants' persistent writes until the final acknowledgment. All captured network leases remain fenced. Observational QUERY does not consume the native mutator sequence; a following RELEASE may use that same next sequence number.

The coordinator must retain exact controls when delivery or acknowledgment is uncertain. The service validates correlation and monotonic mutator receipt order, but it does not attest an adversarial client's memory or replace the C endpoint's admission and typed payload validation.

## Cancellation and recovery boundary

Before START authorization, `cancel(...)` or trusted `refused(...)` clears consent. If no BIND was ever authorized, the challenge can abort immediately. Otherwise it remains ABORTING until `aborted(..., request, response)` acknowledges native ABORT for every possible hold. A lost BIND reply or an inactive query is not proof that a hold never existed. Repeated refusal cannot resurrect an already acknowledged abort.

After START authorization, timeout, disconnect, changed canonical head or conflicting native data produces RECOVERY_REQUIRED. No automatic abort, winner, forfeit, generic reset or gameplay release follows. A freshly authenticated lease may inspect the retained state but cannot mutate the old captured lifecycle. Recovery-required rooms remain busy and are never evicted by the terminal-history limit.

This service is intentionally in memory. Restarting its host loses uncommitted service history; it therefore cannot be exposed as complete restart-safe battle coordination. Durable journals, canonical closed-core recovery, authoritative result policy and launch admission must be integrated before shipping. Four-person consent and lifecycle validation do not establish playable full-six-per-trainer Multi: native engine integration and an actual four-core battle remain required. Championship, wagers, statistics and rewards also remain pending. The owner's interrupted-battle policy has not been selected.

## Verification

On October 8, 2026, the affected Desk/arbitration/team group passed **82 tests per system**, with zero skips: Windows 50.758 seconds and WSL 95.306 seconds. It includes the original 27 singles Desk cases, nine new Multi Desk cases and three new four-party arbitration cases. The native receipts in these tests are simulated; the encrypted Flash fixtures, SQLite heads and arbitration TCP sessions are real.

These tests exercise authenticated actor separation; immutable slots, heads and RNG; separate consent from all four trainers; fixed duos and format conflicts; all-four registration, PREPARE/START and complete-party barriers; lost BIND acknowledgments; partial aborts; exact and changed replay; malformed roles/generations; equal and conflicting results; all-four release acknowledgments; expiry/disconnect barriers; bounded history; and monotonic-clock/type validation. The server cases verify that a fourth participant's upload blocks BIND and that partial abort/release never frees another participant early. Fixture success establishes these state transitions, not a playable native Multi battle.
