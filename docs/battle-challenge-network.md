# Authenticated battle invitations

The companion now exposes `battle_challenge_rpc` with invite, invite_multi, accept, cancel, status and pending operations. Each operation derives its actor from the authenticated world connection. A singles invitation requires the other trainer's exact fingerprint consent; a full-party Multi invitation requires all three other trainers to accept independently. The pending list contains only the requesting player's active room. Repeated invitation IDs preserve the original roster, generation and RNG allocation.

This adds the control path needed by player menus. It does not dispatch native commands. No public operation can register a native incarnation, authorize BIND/START, submit restoration receipts, declare a winner, or release a party. A cancellation after possible BIND remains aborting until the trusted coordinator supplies the required native acknowledgments. Post-start cancellation retains the existing recovery boundary. The server's `development_battles` option still defaults to false.

Responses expose canonical party counts and checkpoint identities for consent, but never the other trainers' save payloads or native battle RNG. Strict request and response schemas reject actor impersonation fields, execution commands, changed team membership, malformed counts, foreign challenge replies and mismatched generations. Connection loss fails pending RPCs with unknown fate; reconnect requires an authoritative status read. No request is automatically accepted or replayed.

## Reuse audit

This adaptation uses the existing project BattleDesk, authenticated asyncio connection, bounded queues, ownership leases and strict team-protocol UUID validation. The accepted native source is `afd92ce3a12204873e2f06a77a7bf1717d04f53b`, derived from RHH 1.17.1. Current upstream `6057b187f946094d614e9c34bc12731ea6a5b7bb` and the [official feature catalogue](https://rh-hideout.github.io/pokeemerald-expansion/) provide link menus/controllers, rather than this project's independent four-client TLS world service. The [existing reuse audit](customization-and-reuse.md) records the compatible community review and save/multiplayer conflicts. The [Python streams documentation](https://docs.python.org/3.14/library/asyncio-stream.html) supports reusing the established reader/writer lifecycle. No new dependency or external code was incorporated, and no save schema, mailbox ABI, engine revision or gameplay rules changed. Performance over Wi-Fi/Internet remains unmeasured.

## Verification

Windows Python 3.14 passed 95 affected tests in 44.382 seconds, with no skips: the ten new strict protocol cases and eight new four-companion TCP cases, plus the existing battle Desk, Multi Desk, arbitration, team network and companion suites. The new tests exercise separate four-player consent, exact retry, default-disabled behavior, participant privacy, stale consent, reconnect invalidation and retained possible native holds. They use genuine SQLite ownership checkpoints and authenticated TCP clients with fixture Flash/native receipts. They do not establish in-game menu, actual-core battle execution, durable restart settlement or separate-PC acceptance.
