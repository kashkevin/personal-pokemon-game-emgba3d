## What changed since run 367's build

The app's `8a4b96d` (the launcher only); the engine and the GBA ROM unchanged. What a player meets:

* **A save this PC could not store is refused definitely, and saving goes on (MS-215, Medium)** (app `8a4b96d`): when
  the disk of the PC that plays is full (not the host's), a save to a world (Save now, an in-game save in a world, the
  autosave) cannot write its journal, so nothing is sent and nothing is damaged (the world keeps the previous save). The
  launcher then stopped saving for that game and said "This save needs recovery. Close the game and reopen through Host
  Game or Join Game." - and closing the game, as told, ended the progress since the last save, which only the running
  game held. Now that save is refused as definitely as one a busy game refuses, and saving goes on: the launcher and the
  in-game session window say "This PC could not store the save (its disk may be full), so it was not sent. Keep the game
  open: your progress since the last save is only in the game until a save works. Free some space on this PC, then press
  Save now, or wait for the next autosave.", the in-game save's banner "This PC could not store it. / Free some space,
  save again.", and the autosave tries the same save again a minute later. No stray save file is left behind, and the
  host-loss saver forgets the export the game let go, so a host loss from then on makes a new emergency save. A disk that
  fills after the world stored the save is handled as before (the save is in the world; reopening resolves it exactly).
  Found by filling a real disk to its last byte (L: TEST_LEDGER "Save integrity: the player's own disk full").
