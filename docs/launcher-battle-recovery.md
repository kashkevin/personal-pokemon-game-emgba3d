# Launcher recovery for a retained multiplayer battle

The launcher's **Recover battle** action connects the existing retained game to `NativeBattleRecoverySession`. It is available only for an exact verified `battle_resume_abi_version=1` and `emergency_save_abi_version=2` installation and an unresolved resumable battle belonging to that same live game, runtime, bridge object, incarnation, native runtime ID, original authenticated session and canonical checkpoint. Installing a new manifest or seeing a recovery file does not grant authority. The host enables its resume service only when that optional capability is present in the verified manifest.

The launcher records those original objects and identifiers synchronously when the native Players-menu Enter event arrives. The exact displayed accepted challenge is claimed before asynchronous work; `_native_menu_capture_battle` publishes the immutable provisional intent and reserves the interaction before returning. This uses the original authenticated launcher binding, including after a fenced idle disconnect, and never substitutes replacement authentication. The native Enter latch remains required while publication and later preparation happen. The asynchronous preparation consumes only that same menu and immutable challenge, drains autosave and transfers the hold through ADMIT. Only the same task and menu may finish the acknowledged atomic CLOSE handoff; failure retains the original core and intent. A resume-capable launcher refuses the older close-first battle path.

A cold launcher, replacement core, replacement bridge with the same numeric incarnation, altered intent, foreign checkpoint or unresolved save/trade/emergency export cannot use recovery. Both provisional and full original intents are recognized. If conversion already occurred, `verify_admission_conversion` must prove the archived original admission, exact ADMIT receipt and full original BIND before the launcher replaces its retained typed intent. Ordinary autosave, manual save and overlapping interaction work remain excluded while recovery runs. The worker accepts a single explicit click and waits for the original participants; it cannot choose an outcome, cancel the battle, launch a replacement game or invent a new checkpoint.

The recovery client owns reconnect, native reconciliation and durable completion evidence. The launcher retains the original intent while a recovery is incomplete. It adopts a renewed session only after a typed `BattleCompletion`/`RenewedBattleSession`, the unchanged canonical revision/hash, current authenticated identity, and the same original objects all agree, and `verify_recovery_completion` validates the durable terminal receipt for successful native RELEASE and host closure. A connected player whose peer disconnected may retain the same authenticated lease; a changed session must never move its epoch vector backwards. An equal lease cannot substitute a different server epoch.

Normal resumable battle completion and recovered completion share the same terminal adoption helper. Native RETIRE leaves a field hold while the previous emergency-save controller is retired through its exact terminal verification API. That old controller is never rearmed or given a cleared loss event. An observer which never armed may be discarded only when it is still unregistered and has no bound session, bridge, task or loss. The old observer is drained before a fresh controller performs its own safe native BIND, ownership grant and awaited arm. Only the verified registered successor may complete HANDOFF21 and release the native hold. A build without emergency ABI2 cannot use this handoff. The launcher then adopts the renewed binding, preserves the user's autosave preference, starts a fresh five-minute deadline and permits manual saving from the unchanged checkpoint base.

After verified HANDOFF and the final same-core check, the launcher also retires the matching Python menu admission latch through `finish_battle_admission(battle_id, generation)`. This only releases UI bookkeeping for that exact original challenge so the player can reopen Players later. It cannot authorize native release. A mismatch retains the original terminal intent and successor for investigation/retry; a headless battle with no menu admission is a no-op.

If terminal evidence was written but launcher adoption failed, the retained original intent permits a retry through the client's terminal path, even after the pending intent was removed. This is still limited to the unchanged live game and authenticated authority. Failure while arming the successor or acknowledging HANDOFF retains that exact successor for retry; it does not retire the old controller again or construct over a registered successor. Refusal, uncertainty or cancellation retains the core and bounded recovery status; raw transport errors, file paths and credentials are not shown. Closing the launcher while recovery is unresolved does not destroy the retained game. If the game itself exits, the launcher cancels and drains recovery before the runtime releases its file lease.

If that exact registered successor later completes host-loss preservation, its finished typed `preserved/can_close` receipt may allow ordinary closure even while the earlier terminal-handoff failure flag remains. The gate requires the same original game, runtime, bridge, incarnation, native runtime ID and checkpoint base, matching successor identity, completed controller task, and absence of a pending provisional or full battle. This does not resume gameplay, adopt a new launcher binding or delete terminal evidence. An unfinished, uncertain or foreign controller still retains the core. Cold-start export reconciliation remains the existing separate recovery path.

## Reuse and scope

This composes the project's existing native battle journal, checkpoint ownership, `PlayerRuntime`, verified installation, emergency controller and Tk/asyncio worker queue. It adds no dependency, native opcode, encounter probability, save layout or gameplay rule. The engine/upstream/community review remains recorded in [native battle execution](native-battle-execution.md#research-and-reuse) and [the customization/reuse audit](customization-and-reuse.md). The separate native resume implementation and host reconstruction own their protocol and acceptance evidence.

## Validation and acceptance limits

The initial launcher focus passed 13 of 14 methods; the remaining fixture used a synchronous `AsyncMock` callback which returned an unawaited coroutine. Replacing it with an explicitly awaited asynchronous callback produced **14/14 PASS in 0.453 seconds**, with no skips. The retained private log is `root-delivery-recovery-windows-4.log`, SHA-256 `4f20bd32a72da0af300189d4ae937d9691ed41a70c2454670ba53c8818c610d4`.

After correcting the no-emergency-capability cleanup, the complete affected launcher cohort passed **83/83 methods in 62.320 seconds**, with no failures or skips: all fifteen new recovery checks plus 68 existing session, autosave, exit, GUI and interaction checks. The retained private Windows log `root-delivery-recovery-windows-5.log` has SHA-256 `95998aff5f50d8a8c04441a2fbc1a56cbce46a11331eef6cf711f7d91a612f57`.

The subsequent explicit RETIRE/HANDOFF extension requires emergency ABI2, replacing the earlier no-emergency success case with a capability refusal. All **18 launcher recovery methods and the same 68 existing launcher methods passed** in the 133-method Windows integration run. That aggregate run had one unrelated client refusal-message fixture failure and is not recorded as a full-suite pass. Its log `integrated-terminal-windows-1.log` has SHA-256 `ef867c058f173bd01d17eceb94abe0fe0555b931f8f93718826ba091d0ed1f2d`. New cases cover ordinary battle completion through the shared helper and exact successor reuse after arm or HANDOFF failure.

The first provisional integration passed **92/92 methods in 61.662 seconds** (24 recovery and 68 prior launcher methods), with no skips; retained log `launcher-provisional-windows-1.log`, SHA-256 `5c9cc2c36115a79933ccc74c7ce19e8d64c2a62f212a68290251aff41c967cdc`. After moving durable capture into the synchronous Enter event and adding the exact-successor preservation closure gate, the final affected cohort passed **96/96 methods in 57.892 seconds**, with no failures or skips. Its private log `launcher-provisional-windows-2.log` has SHA-256 `89f9a78569dbb54e281e346a6ae859e997d99917e93e852eeaf680e32e52e604`. The 28 recovery checks include real provisional record publication before any async preparation, offline original-binding capture, partial conversion refusal, uncaptured Enter refusal, same-task/menu/consent ownership and successor preservation/foreign-core boundaries.

The final UI-latch retirement sequencing and refusal checks increased recovery coverage to 30 methods. All **70/70 combined menu and launcher-recovery methods passed in 7.019 seconds**, with no skips, after this delta: private log `menu-admission-windows-2.log`, SHA-256 `5c6fbaca324193157a3b673268bb2186dcee946e046946e23d5e8c07ba480d4a`.

The tests use strict native binding/intent data, typed completions, explicit transport/service fixtures, a real threaded worker and real Tk widgets. They cover identity/refusal boundaries, duplicate clicks, cancellation, terminal-adoption retry, controller retirement, fixed UI messages and process-exit drain order. They do not establish an actual-core resumed battle, a packaged recovery-button playthrough, four-player reconnect acceptance, or Wi-Fi/Internet acceptance.

The previously qualified combined game at engine `1a7a0cdb5dadd2820a3b6c25c4ecafce1facd6eb` has no resume marker. Its older manifests, frozen packages and accepted evidence remain unchanged, and the new recovery action stays unavailable on that build. Enabling the action in a release requires a separately qualified exact native build, manifest and runtime bundle.
