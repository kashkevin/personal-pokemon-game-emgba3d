# Native trade effects: preparation boundary

The existing transaction still implements [`simple-owned-party-exchange-v1`](trade-eligibility.md). Its exclusions remain active. Native effects need a separate prepared-result capability before the server can publish anything beyond the exact offered record exchange.

## Gen 6 friendship must be explicit

The accepted baseline is Gen 6. The existing [Gen 6 foundation audit](gen6-foundation-update.md) already requires `P_UPDATED_FRIENDSHIP = GEN_6` with the rest of the species profile. The pinned `include/config/pokemon.h` currently sets it to `GEN_LATEST`; `include/constants/pokemon.h:STANDARD_FRIENDSHIP` therefore resolves to 50 for affected species, whereas its pre-Gen-8 value is 70. Some species have explicit nonstandard values. Replacing `TradeMons`'s hardcoded 70 with the current species table would still mix profiles. No configuration or ordinary friendship behavior is changed by the preview.

PKHeX's inspected Gen 6 logic uses separate original and handling-trainer friendship values, initializes a new handler from species base friendship, and preserves the opposite value in certain Return/Frustration handler transitions. This suggests additional handler-history requirements that a single GBA friendship byte cannot fully represent by itself. The final implementation needs an explicit Gen 6 species table and a deliberate persistent representation, preserving the accepted rules rather than silently dropping an exception. This Pokémon friendship state is unrelated to the project's later player-pair/Lucky progression.

## Read-only native preview

The isolated native addition is `include/multiplayer_trade_effects.h`, `src/multiplayer_trade_effects.c` and `test/multiplayer_trade_effects.c`. `MultiplayerTradeEffects_Preview(received, sent, out)` observes two already owned party records and returns a versioned 36-byte result. It clones the records before native decryption/validation and uses only `GetEvolutionTargetSpecies(..., EVO_MODE_TRADE, ..., CHECK_EVO)`. Item consumption, species mutation, stats, moves, friendship, Pokédex, mail, RNG and save state remain untouched.

The result binds observed serials, species, incoming PID/OT, held item, current friendship, native evolution target and the **observed pinned** base friendship/config generation. Flags identify eggs, mail references/items, forms outside standard IDs, native forbidden species, evolution, handler friendship and Return/Frustration. Every valid result always carries `POLICY_REQUIRED`; invalid/unassigned/duplicate records return failure with no stale populated plan. Output aliasing either input is refused. This is a native rule-query seam, not a new mailbox command, authenticated offer, post-image authorization or enabled gameplay capability.

The preview intentionally reports the current profile instead of presenting its base friendship as Gen 6. It requires initialized native game context and addressable party records: the reused evaluator reads weather/item context, and this API is not a validator for arbitrary pointers. Any future IPC caller must admit it only at a safe native phase. A future server/companion preparation must bind this observation to the exact authenticated world, lease, build, immutable offer generation, both checkpoint revisions/hashes and recipient. It must not use the serials or `POLICY_REQUIRED` result as authority by themselves.

## Paired native preparation still required

Both final native results can exist before one paired commit, but only after each recipient has completed any permitted evolution/move decisions. The current preparation checkpoint freezes each player's original save. A separate future native preparation phase must retain that original authority while receiving the counterpart's exact offered record, performing only qualified effects, collecting ordinary decisions and exporting a frozen candidate. It must prohibit field progression and native link saves throughout; memory use must fit the measured EWRAM/heap budget rather than assuming another full Flash buffer is available.

The server needs a versioned validator for those candidates. [`trade_flash.validate_party_swap`](../src/emerald_multiplayer/trade_flash.py) currently reconstructs the exact 100-byte exchange and rejects every other change. [`TradeCheckpointStore.commit_trade`](../src/emerald_multiplayer/trade_storage.py) and its full immutable-history replay both apply that rule. The new capability must specify and reconstruct exact allowed Pokémon changes, received/evolved Pokédex bits, recipient mail slots/payloads, ribbon presentation and exactly-once statistics. It must preserve all unrelated save fields and every other Pokémon; allowing arbitrary changed sections or trusting a client-supplied hash is insufficient. The same capability/version and choice evidence must remain verifiable during history replay.

Only after both independently prepared candidates pass may the existing atomic SQLite group transfer ownership, publish both canonical heads and create recovery receipts. Repeated receipt delivery must reuse those exact bytes, without replaying item consumption, evolution learning, Dex/stat updates or Lucky effects. Before publication, abort restores the original retained authority; after publication, recovery installs the recorded outcome. Durable prepared-state and lost-result boundaries need explicit journal tests before a player-facing offer can use this capability.

Traded eggs additionally require an authorized hatch transition: pinned `egg_hatch.c:AddHatchedMonToParty` changes OT fields, while current ordinary history rejects a changed immutable origin. Preserve the immutable birth/trade history separately from legitimate native hatch provenance. Mail needs recipient-local allocation and transfer of its payload, never a copied sender index. Accepted forms and Gen 6 evolution cases need their own catalogue/fixtures. Existing temporary eligibility exclusions remain until these paths are implemented and qualified; none is treated as a permanent gameplay removal.

## Qualified preview slice

Engine commit `bf47ca5bb77f0b96b7858856b1ab20e7ff23abe3` contains only the three new native preview files, based on `84a4d1c`. The normal build completed without warnings. The native `TESTS=Multiplayer` group then passed **87/87 cases**, including eight new preview tests, with no skips or unexpected failures. Coverage includes all 24 encrypted layouts; byte-identical inputs, save blocks/storage and both complete RNG states; unchanged save counter; native held-item/partner/Everstone/Kadabra rules; unresolved egg/mail/form/handler flags; checksum failure, nulls, duplicate/unassigned identities, and output aliasing. A test-only scalar RNG comparison was corrected to compare the actual complete `Sfc32State` structures before this successful run.

An independent read-only native review found no blocker. Both builds used one worker and byte-verified independent build caches; their final logs contain no clock-skew warnings. Normal memory usage was 233,428 bytes EWRAM and 28,376 bytes IWRAM. These are build figures, not a measured per-frame preview cost. There was no full native regression or actual-player trade run for this isolated addition, and its helper has no production mailbox caller.
