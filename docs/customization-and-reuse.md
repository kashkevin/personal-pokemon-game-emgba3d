# Character customization and existing system reuse

This initial audit supports the [combined user amendment](project-update-customization-friendship-shiny-charm.txt) and [current delivery order](development-roadmap.md). Reuse the pinned expansion's existing mechanisms, keep safe trading next, and prototype customization with reusable art layers composed into ordinary animated sprites. This is an architecture recommendation; no creator, new artwork, friendship/Lucky system, Charm reward, or runtime migration is implemented by this update.

## Audited versions

The accepted engine remains ownership source `88c7ef798ab5f91a496099cc687252fa5c4b12a3`, derived from RHH `expansion/1.17.1` / `bb1093a7c72d3961d9a37d8e02ad2abc2c866682`. The current upstream was also checked: GitHub's latest release resolves to [1.17.1](https://github.com/rh-hideout/pokeemerald-expansion/releases/tag/expansion/1.17.1), and its observed master head was [`6057b187f946094d614e9c34bc12731ea6a5b7bb`](https://github.com/rh-hideout/pokeemerald-expansion/commit/6057b187f946094d614e9c34bc12731ea6a5b7bb), committed October 6, 2026. These observations do not authorize an automatic upstream merge.

Local source inspection and current upstream configuration agree on the reusable mechanisms below. The upstream phrase “Full Trainer customization” describes trainer Pokémon/team data, not a layered player clothing creator. Followers, modern data, battle systems, dynamic overworld palettes, expanded graphics identifiers, configurable mechanics, RNG tools, and menus are already supplied as components. Their presence does not establish the project's complete gameplay or multiplayer acceptance. ## Recommended rendering approach

Author aligned reusable body, hair, top/jacket, bottom, hat, shoes, backpack and accessory layers for every supported pose. Compose the visible result into a conventional 4bpp avatar frame, with a bounded cache refreshed on pose or appearance change. Reuse the engine's ordinary animation, priority and object-event handling. This avoids storing every possible complete outfit combination in ROM while retaining one principal sprite per avatar.

| Approach | Tradeoff |
| --- | --- |
| Separate runtime sprites for every clothing layer | Convenient independent pieces, but multiplies sprite allocation, positioning, sorting, reflections and field-effect work. Four avatars with six layers need 24 engine sprites before followers/NPCs/effects. Reject as the default until a measured prototype justifies it. |
| Prebuild every complete sprite-sheet combination | Simple playback, but combinations grow multiplicatively and consume ROM/art build time. Suitable for a small preset catalogue, not the full option target. |
| Compose reusable layers into bounded cached frames | Recommended prototype: bounded sprite count and reusable art, at the cost of a compositor, palette contract, cache lifetime rules and timing measurements. Cache active poses, not every state sheet for every player. |

The pinned source has 16 active ObjectEvents, 64 engine Sprite slots, 32 KiB OBJ VRAM, and 16 object palette banks. Ordinary map setup reserves 12 banks, while a reflection-related path reserves eight; the remainder is shared with effects/UI. Allocation is map-dependent, and additional palettes cannot simply be assumed free. A 4bpp avatar has 15 visible palette entries plus transparency, requiring deliberate shade allocation across clothing, skin and hair. Different players need independently managed palettes; recoloring the shared Brendan/May palette would change other actors too. Reflections, weather, fades, followers, NPCs and menu transitions must respect the allocation scheme.

The local audit measured 40,192 bytes for one body's uncompressed native state sheets; four complete caches would require 160,768 bytes, exceeding the existing 115,968-byte heap by themselves. As an illustrative starting budget, two 512-byte frame buffers per avatar would total 4 KiB for four avatars, plus metadata/palettes. This is not proof that rendering, decompression or all poses fit their frame deadlines. Measure both heap high-water usage and frame/VBlank work with four avatars and followers before selecting final cache sizes.

Budget and adapter references in the unchanged baseline: [`include/constants/global.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/bb1093a7c72d3961d9a37d8e02ad2abc2c866682/include/constants/global.h), [`include/sprite.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/bb1093a7c72d3961d9a37d8e02ad2abc2c866682/include/sprite.h), [`include/gba/defines.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/bb1093a7c72d3961d9a37d8e02ad2abc2c866682/include/gba/defines.h), [`include/malloc.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/bb1093a7c72d3961d9a37d8e02ad2abc2c866682/include/malloc.h), and [`event_object_movement.c`](https://github.com/rh-hideout/pokeemerald-expansion/blob/bb1093a7c72d3961d9a37d8e02ad2abc2c866682/src/event_object_movement.c). Reuse its graphics-switching and palette allocation functions, but audit the existing compressed-sheet reallocation TODOs before adopting its caching path. Native animation coverage is in [`object_event_anims.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/bb1093a7c72d3961d9a37d8e02ad2abc2c866682/src/data/object_events/object_event_anims.h).

Mirroring is acceptable only when accessories and the source animation permit it. The current remote presence prototype represents fewer states than the full game; expand its pose model deliberately. Battle front/back portraits and Trainer Card graphics need their own assets/adapters.

## Appearance persistence and synchronization

Use a compact versioned descriptor: catalogue/schema version, body, skin, hair style/color, clothing/accessory IDs and palette choices. Exact field widths follow the asset catalogue and validation rules; do not transmit arbitrary images or unbounded filenames. Bind the catalogue to the compatible build/ruleset.

Persist a validated appearance revision in the player's authoritative profile. Send the descriptor on join, appearance change and reconnect; movement references its revision and pose. Remote clients use their identical local catalogue to construct the same appearance. Validate component combinations and eventual unlocks, and apply changes only after durable acknowledgment. Recovery must not let an older save silently revert a newer accepted profile appearance.

The current 128-byte presence ABI validates reserved bytes and cannot silently absorb this descriptor. Version the protocol/mailbox and save/profile format, with explicit migration and mismatched-version rejection. Reuse existing rendering/field-effect hooks rather than unrestricted emulator RAM writes. Prototype four distinct appearances, mutate one, change maps and movement modes, reload/rejoin, and verify every observer sees the same result without palette contamination. Implement early-game creation after core multiplayer proof, followed by later-change UI, cosmetics and advanced cards.

## Trading, friendship and Lucky integration

Reuse the pinned [`trade.c`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.1/src/trade.c) presentation and audited Pokémon transformations. Native link exchange alone is insufficient: the current ownership store intentionally rejects foreign IDs and unjournaled disappearance. Safe trade needs paired canonical revisions, immutable birth/allocation provenance separated from current ownership, explicit transfer events and globally ordered integrity replay. Never simulate a trade by retiring an ID and minting a replacement or by weakening ordinary checkpoint validation.

A paired transaction also needs a deliberate hold/keepalive and recovery protocol: the existing export `END` releases a ROM, and its watchdog can resume an uncommitted export. Freeze/confirmation, commit and post-image import must remain coherent across both participants even when one disconnects. Reserve a durable transaction ID, both base revisions and offer fingerprints, globally ordered events and versioned outcomes. Audit trade evolution and an egg's later original-trainer transition at hatching without broadly relaxing identity validation.

Existing [`PokéNav list machinery`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.1/src/pokenav_match_call_list.c) can support Friends UI, but its NPC contacts and Pokémon friendship fields are not player-pair relationships. Key new relationship records by world plus a canonical unordered pair of player UUIDs. Record meaningful activity and trade IDs idempotently; team changes and competitive results do not reduce friendship.

Later Lucky conversion must retain the original world/instance ID, personality, original trainer and protected attributes. Store a single committed outcome and approved IV deltas with both trade post-images. Retried delivery cannot reroll the outcome; the guaranteed Lucky Friends flag is consumed only by that same successful transaction. Design Lucky metadata, trade history and summary presentation together; the spare Pokémon bits used by ownership are already occupied. Use versioned extensions/migrations rather than unreviewed bit reuse. Thresholds, eligible trade types, IV floor/improvement algorithm, both-side treatment, repeated Lucky conversion, chances and secondary benefits remain unselected. Raising IVs can change Hidden Power's type through IV parity, even without decreasing an IV; resolve that trained-Pokémon compatibility question before implementing conversion. Do not import unrequested Pokémon GO restrictions such as preventing retrades. [Existing Hidden Power calculation](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.1/src/battle_main.c)

Emerald Rogue provides [interaction/trade examples](https://github.com/Pokabbie/pokeemerald-rogue/blob/5ccb74cf1ef2c0349dfa5d70883b030bbc9ff803/data/scripts/Rogue/Rogue_Multiplayer.pory); [Celio's emulator bridge](https://github.com/Celio-Link/Celio-mGBA-Link/blob/5f29daba2a331f721203f430b28750e72e68ac02/README.md) and [Wired-Ariel's GPL-3.0 project](https://github.com/Wired-Ariel/gen3-poke-multiplayer/blob/01e43f5b5e415ef2511974c5f9e0ec34d18e7a9e/README.md) are further transport references. Their dependencies, link-oriented behavior and lack of our canonical paired-save contract preclude treating them as an accepted substitute. The current bounded mailbox and server ownership guarantees remain the integration boundary.

## Shiny Charm and Game Corner integration

The pinned engine already defines the Charm key item/icon and a generation-time reroll hook. Current upstream likewise sets two additional Charm rolls, but also defines `SHINY_ODDS` as 8 over 65,536. Thus the accepted networking build is not evidence that the requested Gen 6 shiny profile is configured. Research exact Gen 6 encounter-specific behavior and test it before changing odds; this audit records existing code, not approved final probabilities. [Charm configuration](https://github.com/rh-hideout/pokeemerald-expansion/blob/6057b187f946094d614e9c34bc12731ea6a5b7bb/include/config/item.h), [current shiny constant](https://github.com/rh-hideout/pokeemerald-expansion/blob/6057b187f946094d614e9c34bc12731ea6a5b7bb/include/constants/pokemon.h)

Reuse the existing [Mauville prize scripts](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.1/data/maps/MauvilleCity_GameCorner/scripts.inc), coin APIs and casino activities. Adapt coin check/deduction, bag-space handling and guaranteed award into a durable personal purchase that refuses duplicate rewards and survives interruptions. Price and earning balance remain pending. Encounter generation must explicitly distinguish eligible personal rolls from server event properties so the Charm and Local Soft Reset never modify a shared event or another player's odds. This work remains behind the foundation priorities.
