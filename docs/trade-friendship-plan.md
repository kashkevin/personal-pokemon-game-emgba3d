# Bounded Gen 6 trade friendship plan

`trade_friendship.py` supplies a pure planner and exact encrypted-record transformer. It has no production caller, database migration, native command or trade eligibility grant. The existing `simple-owned-party-exchange-v1` capability and all its exclusions remain unchanged. Its internal plan identifier is `gen6-handler-friendship-plan-v1`; this identifier is not an advertised trade capability.

## Reuse and source pins

This slice extends the [native effects audit](native-trade-effects.md). Read-only upstream checks on October 8 returned RHH `7b95be15d84a053948791ce91e5dec0b168947a5` and PKHeX `66ef5983a5d349efa2dd615f2926a1b1ee97306e`. They do not replace the installed RHH `bb1093a7c72d3961d9a37d8e02ad2abc2c866682` base or accepted build pins.

The refreshed RHH [trade implementation](https://github.com/rh-hideout/pokeemerald-expansion/blob/7b95be15d84a053948791ce91e5dec0b168947a5/src/trade.c#L2922) still assigns a fixed received friendship of 70 and couples the surrounding flow to native link/mail/Pokédex state. It does not provide the separate Gen 6 handler history or this project's paired authoritative transaction, so importing the whole newer trade flow would not resolve these requirements.

PKHeX's pinned [G6PKM handler implementation](https://github.com/kwsch/PKHeX/blob/66ef5983a5d349efa2dd615f2926a1b1ee97306e/PKHeX.Core/PKM/Shared/G6PKM.cs#L84) is primary implementation evidence for switching the original/handling selector and copying opposite friendship for Return/Frustration only when that selector changes. Its [PK6 handler implementation](https://github.com/kwsch/PKHeX/blob/66ef5983a5d349efa2dd615f2926a1b1ee97306e/PKHeX.Core/PKM/PK6.cs#L394) matches original identity using name, gender, ID and origin game, while handling identity uses name and gender. A new handling trainer receives species-base friendship, with an additional geographic refresh condition. This is the project's community implementation evidence, not official game-code certification.

No PKHeX code, .NET runtime or package is imported. The upstream GPL-3.0-or-later licensing and representation differences remain recorded in the earlier audit. The existing pinned ownership decoder, checksum validation and native party bounds are reused locally. The four encrypted substructures, their 24 permutations and UID locations remain those already qualified for the ownership save profile. Nothing is added to the incorporated-dependency ledger.

## Representation and refusal boundaries

`FriendshipHistory` retains the immutable owned serial, full original identity, both friendship values, handling identity and current selector. The exact offered native friendship byte updates the active retained value before computing the recipient's state. The output is a new immutable history record; the input is untouched. Unknown legacy history is refused, including a missing opposite value. A single GBA friendship byte cannot reconstruct that history.

The caller must supply a verified Gen 6 species-base value and an explicit, separately qualified geographic-refresh decision. This slice deliberately does not assume that `P_UPDATED_FRIENDSHIP = GEN_LATEST` yields Gen 6 values, or silently map absent GBA geographic fields to a Gen 6 condition. Both adaptations remain production gates. New handler selection and a change between original and handling selectors are separate facts: a Bob-to-Carol trade stays on the handling selector and therefore does not copy the old value solely because Return is present.

`transform_received_party_record` accepts one immutable 100-byte owned party record. It validates occupancy/checksum, serial and retained original identity, decrypts a copy, changes only growth friendship, recalculates the checksum and re-encrypts. Native move IDs are masked to 11 bits when identifying Return/Frustration; UID bits above those moves survive unchanged. Header/party data, other secure bytes, PID, OT, species and ownership remain exact. Eggs are refused because their corresponding byte stores hatch cycles.

This helper grants no authority to trade a species, process mail, evolve a Pokémon, update the Pokédex or alter statistics. It is not a complete legal-Pokémon validator. Production integration still needs authenticated retained history by owned serial, checkpoint updates, exact paired post-image validation, atomic history publication/replay, explicit migration, a generated Gen 6 base table and native preparation/recovery qualification. Its inputs must eventually be derived from those trusted bindings rather than supplied by a client.

## Exact paired Flash preparation

`trade_friendship_flash.py` adds the validator prerequisite for a future store capability. It accepts two canonical `Checkpoint` records and two typed retained-history plans. It verifies source payload hashes, revision bounds, player/ownership agreement and matching build/rules/profile, then reuses the current same-world, disjoint-inventory and temporary eligibility checks. The recipient's name, gender and trainer ID are read from its validated canonical Flash. Profile game version remains an explicit trusted adapter input.

Both incoming records are transformed independently and inserted with the existing checksum-aware party-section writer. The returned input digest includes the plan version, world, build/rules/profile, profile game version, both source player/revision/request/hash envelopes and every supplied history/policy field. The outcome digest additionally binds both complete outputs and resulting histories. Retrying identical preparation produces the same results. `validate_friendship_pair` reconstructs and compares both complete Flash containers, preserving previous banks, RTC footers, unrelated party/storage, money, progression and every other byte outside the two replaced records and their sector checksums.

This code does not connect to `TradeCheckpointStore.commit_trade` or its history replay. Both still call the existing exact-record validator. Tests explicitly require that existing validator to reject a newly changed friendship candidate. The **five paired-Flash tests passed on Windows in 5.167 seconds**, with no skips, including full-output rejection, exact repeat/bindings, recipient identity, unknown-history refusal, counter wrap and previous-bank/RTC preservation. The private `friendship-flash-windows-2.log` SHA-256 is `7f160f9d365e4a0e8d8ee07c4c2ee57adddecef5616c5c95ee8a754b7a8f0914`. An earlier aggregate retained fixture failures because its synthetic current/previous banks had different trainer IDs; correcting both valid banks to the same test character fixed that setup without weakening validation. Production preparation authority remains pending storage/native qualification.

## History integration audit

The current schema-3 store records globally ordered checkpoint and paired-trade groups, ownership memberships, original acquisition provenance, and exact payloads. `_audit_history` reconstructs ownership and revalidates every historical pair using the same exact-record rule as publication. Friendship state must participate in that same transaction and replay; a separately committed sidecar cannot provide the required atomicity.

The existing optional schema offsets are +100 for battle reservations and +200 for personal reset attempts. The observation prerequisite below uses +400 on trade schema 3; this is separate from any future capability that authorizes effects. Original-trainer identity matching alone cannot establish that an imported Pokémon was never traded. Trusted native acquisition provenance and the legacy partial-history policy remain necessary before enabling the new effects.

## Same-database observation prerequisite

`trade_friendship_observations.py` implements an optional immutable observation ledger within the existing SQLite world. `enable_friendship_observations` requires an idle trade world, a new consistent backup whose schema/data are reopened and compared, then one transaction that creates the extension and backfills every historical canonical checkpoint. Failure before commit rolls back the extension and backfill while keeping the backup. Merely opening an older world creates nothing. The strict recognizer supports exact combinations with battle/reset extensions; ownership-only schema 2 keeps its existing +100/+200 support and refuses +400.

This follows the project's existing battle-reservation and personal-attempt migration pattern, reusing the same exclusive owner lock, SQLite transaction, backup comparison, canonical checkpoint parser and schema identity check. No database framework or third-party implementation is added. Its additional storage/whole-history audit cost still needs measurement before selecting it for a downloadable build.

After explicit migration, `TradeCheckpointStore._membership` appends observations inside the same transaction that publishes an ordinary checkpoint or both trade heads. Existing exact-record trade validation remains unchanged. Each observation binds world/player/revision/request/build/rules/profile and the complete source hash, and records only the native original/owner identity, location, species/PID, active byte and its friendship-versus-hatch-cycle meaning. Every observation explicitly says `handler_history="unknown"`, including records whose OT matches their current owner. No missing opposite value is initialized.

All 432 possible occupied locations are supported: party, boxes, daycare and fusion storage. Retired instances retain their historical observations, while authenticated `read_current` requires the current active owner and current lease. Full store integrity reconstructs every row from immutable checkpoint bytes, rejecting deleted, added, reordered or changed facts instead of trusting a stored hash alone. An exact checkpoint/trade retry does not append duplicate observations. This supplies retained native evidence for later history qualification; it is not yet the authoritative two-value Gen 6 handler state and does not enable the prepared friendship candidate.

Thirteen focused methods passed on Windows as part of a **24-test observation/launcher cohort in 11.581 seconds**, with no skips. They cover observation decoding, backfill/migration, atomic checkpoint and paired-trade failure, exact replay, authenticated reads, retirement, tampering, abrupt committed host exit and all six extension orders. The private `root-delivery-windows-5.log` SHA-256 is `6d3c8b979aefc250796d2fa6e73a05edf6eca2268a8226a2bafb2164b53a8730`. Broader affected storage suites remain pending the shared worker handoff. No migration has been run against a private player world by this work.
