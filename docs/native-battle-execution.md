# Native battle execution integration

The source adds an authenticated executor between the Players challenge and the existing native battle mailbox. `NativeBattleSession` runs only after the launcher closes the native menu and observes its newer Close request. The launcher drains automatic saving first. Every participant explicitly enters the accepted challenge; the host waits for all original participants' registered incarnations before issuing BIND. Singles use two trainers and full-party Multi uses four, retaining the existing six Pokémon per trainer.

The client returns only the response to the host's one outstanding command. It cannot request an opcode, seed, party, winner or release. A separate monotonic dispatch ID distinguishes an exact network retry from a later native BUSY retry or read-only QUERY. All envelopes retain authenticated world/player/lease, battle/generation and native incarnation correlation. Before BIND, the client downloads and checks the accepted owned checkpoint without writing it into the game. Its existing BIND journal plus an exact command/response record precede every native dispatch and network acknowledgment. Other save/trade/battle mutations remain excluded for the entire execution.

The host reuses the qualified canonical trainer/party checks, issued RNG, native controller validator and full-Multi delivery barrier: a newly admitted batch reaches every recipient before a later batch is observed. It acknowledges an outbound block only after all peers acknowledge all chunks. A busy recipient leaves its offset and native sequence unchanged. The normal native game supplies choices and the result. The client bridge reads and writes only the allocated production mailbox; no diagnostic party reads, emulator savestates, injected input choices, damage or outcome are part of the executor.

On the pinned ABI 2/3, `restored` is set only after the native return code checks the original party count and PREPARE CRC twice and restores both personal RNG values. `BattleDesk.finish_native` uses that correlated native invariant after all exact startup party blocks have been verified. All participants must report matching fixed-side outcomes before RELEASE; all RELEASE receipts must complete before the host removes the durable reservation. The client archives its completion evidence before removing its BIND admission journal. This does not create a new checkpoint or advance progression.

Host installation explicitly enables the service using `WorldServer.enable_battle_execution` with the string lengths read from the exact hash-verified ROM. New compiler-derived manifest fields are `battle_execution_abi_version=1`, `battle_string_table_address` and `battle_string_table_size=2884`. Their complete optional set, allocation and all pointers are validated. Existing manifests lack this capability and remain gated until regenerated from their matching ELF. No game bytes or native battle ABI are changed by the Python executor.

## Interruption boundary

The execution audit records and same-database reservations survive interruption. They do not restore native RAM or resume an expired ABI 3 core. Native mutation still requires the original captured lease/incarnation; a changed session, missing reply, host shutdown or native refusal retains the reservation and client intent and does not award a result, cancel, forfeit, fabricate a save or launch a replacement core. The launcher must retain the original core while showing recovery required.

Full wait-for-every-participant resumption remains a separate necessary extension: explicit native suspension, same-core lease rebinding, durable reconstruction of host route/controller state and exact outstanding command reconciliation. Changing the current watchdog into an automatic successful release would violate the selected policy and is not implemented. Client process death or power loss is also not recoverable by this source slice.

## Validation

The first Windows focus passed **87 tests in 59.642 seconds**, with no failures or skips, using the pinned provisioning virtual environment. It covers real authenticated TCP and SQLite with two/four client journals, native BUSY retry, forged early RELEASE, corrupt startup, shutdown reservations, and the existing protocol/manifest/journal/admission/desk regressions. Its private log `battle-execution-windows-1.log` has SHA256 `9cf86ae82b95a46540246b021a2088c42fb130083d3d29ebc3958917b308d8af`. Native responses in these cases are explicit synthetic fixtures; this is not playable acceptance. A follow-up **8 tests passed in 1.774 seconds**, including the real Companion IPC command-authority case. After adding same-core second-battle sequence continuity and pre-BIND cancellation, the affected **16 tests passed in 66.183 seconds**.

The first two actual four-core execution runs both failed after 105 complete native blocks. They successfully enrolled four independent six-Pokémon parties and entered native full Multi through authenticated consent, production command dispatch and persistent client journals. Core 1 then reached the pinned engine's `src/sprite.c:437` fatal assertion, “Out of sprite slots,” during the intro. A second run paced near the normal 60fps reproduced the same assertion, excluding the faster original diagnostic pump as its cause. Both runs closed every core and verified the original source-save hashes unchanged. Their private `native-execution-run-1` and `native-execution-run-2` records are failed diagnostic evidence, not acceptance. The next diagnostic captures the read-only sprite pool and native stack to identify the allocator under delayed command delivery.

The delayed intro failure was isolated to overlapping send-out ball particles while four full parties keep more status sprites alive. Native commit `fbe98dc105dafe9a600d51f5f531f3a364671cff` serializes those existing animations using their actual completion flags; it neither raises sprite capacity nor removes the assertion. Its normal build and 80 focused native tests passed. Run 4 passed that intro but reached its 1,800-second proof deadline before the full battle ended; it remains incomplete evidence.

On October 8, **actual four-core execution run 5 passed** with all four trainers owning six Pokémon, 5,232 routed native blocks and 49,092 measured command exchanges. Three trainers selected their sixth slot through ordinary native party-menu input. All four exact original party bytes/counts and Flash saves survived the result and field return, all four ordinary checkpoints retained their owned inventories, and four fresh cores passed ordinary Continue. The proof reports `passed=true`, `cores_closed=true`, and `original_sources_unchanged=true`; its process exited successfully. No diagnostic RAM mutation, savestate, forced winner or forfeit was used.

This frozen run used application source including `18b6478`, the independent-core command batching optimization. Every issued command still persists before publication and each successful receipt persists before acknowledgment; a delivery batch still completes before observing the next.
