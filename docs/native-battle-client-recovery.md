# Retained-core battle recovery client

The optional resume client retains the original native game, bridge object, runtime ID, incarnation, consented roster and canonical checkpoint. It preserves the original pending BIND intent while renewed authentication and host-issued recovery controls are recorded separately. Each mutation requires the exact unanswered control already persisted by the task which owns the live battle and checkpoint lock. An automatic reconnect, replacement core or edited journal cannot acquire that authority.

The client uses the existing checkpoint transport, native control codec, private atomic journal writer and companion IPC. It adds no dependency or save layout. The pinned engine and reuse review remain in [native battle execution](native-battle-execution.md#research-and-reuse); the native resume extension and host replay have separate qualification requirements.

Recovery waits for the original participants without choosing a result or introducing a timeout forfeit. It verifies the same canonical revision and SHA-256 after authentication, keeps lease epochs monotonic, and permits only the original host-authorized route after native suspension and quorum renewal. Loaded records have an exact field set, canonical JSON encoding, bounded dispatch IDs and correlated command/receipt pairs. Durable completion evidence is checked again before a launcher can retire the old emergency-save controller and create a new controller.

For the optional resumable build, the first full BIND also uses a durable admission barrier. The host first replies `admitting`; the client persists that exact BIND and its canonical intent, then acknowledges its SHA-256. Only a subsequent `executing` reply with the identical dispatch may reach the native mailbox. An admitting record grants no native mutation authority. The host owns the all-participant barrier and its replay evidence.

Before that full BIND exists, the exact authenticated Enter choice is published synchronously as `pending-battle-admission.json`. The marked native menu row latches gameplay before sending the choice through IPC. An exact ADMIT transfers that latch into a provisional native battle hold and closes the menu atomically. The preparation helper can finish this original ADMIT while disconnected; it does not download canonical bytes before holding the core. Online preparation records the host Enter claim first, and an uncertain claim reply still drains the exact native hold. Canonical bytes and the accepted party are checked by execution before readiness/PREPARE. Provisional recovery authenticates only the original retained runtime, records the host's original BIND under its original lease/server pins, archives the provisional intent, and acknowledges that exact durable full intent before any BIND executes.

An emergency BEGIN racing the native Enter latch receives the separately gated status 14, `BATTLE_ADMISSION`, before any native save mutation. The controller accepts only an exact original BEGIN refusal envelope, writes and reopens its private refusal archive, then removes only its own still-unstarted emergency intent and reports `battle_waiting`. It does not claim saved bytes or permission to close. A failed receipt write, changed envelope, unsupported capability or PROMOTE refusal leaves recovery held. Synchronous Enter publication may overlap only its matching already-fenced lost controller; native ADMIT continues to require the lifecycle lock.

Both normal and recovered terminal settlement require the authenticated durable host closure and the original successful RELEASE pair. RETIRE is persisted before dispatch and its exact receipt before unlinking the original pending intent. Native RETIRE keeps a separate handoff hold. The launcher verifies the terminal receipt, retires the old emergency controller, and creates/arms a fresh controller under the current authenticated lease before the exact persisted HANDOFF may release gameplay. An uncertain terminal reply is reconciled per original actor without requiring already-finished peers to reconnect. Repeated adoption under unchanged authentication is read-only; changed authentication revalidates host closure and renews only the same core's retirement envelope.

## Actual entry refusal cursor correction

The first two-core native entry run (`native-battle-entry-run-1`, frozen Python `2dba880`, native `aef47e4b28fd6d0e84376961e0cc6632996bb0be`) observed status14 before any provisional file existed, but Python kept `unsaved_held`. The original sources remained unchanged and both proof cores closed. This was a failed acceptance run, not an accepted handoff.

The retained intent and independent command/response hashes identify sequence 39: the request cursor was 0 and the response cursor was 131072 from the previously completed native save stream. Native `PublishResponse` deliberately reports the retained cursor on error replies; it is not a request identity field. Reconstructing the complete typed packets gives command SHA-256 `10796ef9a287b3929900798d9c64a83d67572caa0b132edf1ac9968546b59786` and response SHA-256 `0a4af4bc65f2b75d107e3425e359bbad3b2250d058ccef342fa7e10c9d6b11b6`, exactly matching the actual run.

Refusal correlation now follows the existing Companion transport contract: incarnation, lease, operation UUID, sequence, total size, revision and opcode remain exact; the response's bounded typed cursor and complete bytes remain in the durable refusal archive. The error payload must still be empty. Native source and ABI are unchanged. The regression fixes these actual packet hashes and also rejects forged identity/revision fields or a nonempty refusal payload. An actual entry rerun is required to qualify the corrected composition.

The corrected Windows cohort passed **53 methods in 16.734 seconds**, with no skips, at verified BelowNormal priority: emergency24, client21 and parser8. Private log `actual-admission-cursor-windows-1.log` has SHA-256 `92e66f96499702a521cb4fba77dc647a9284d9ed50c1875d997a1cbf3743e320`.

## Original provisional BIND recovery correction

The later four-core `native-resume-all-run-2`, on frozen application `31e5bf9` and native `aef47e4`, failed at the first recovery BIND after all original participants reconnected. Before that failure, the proof verified four six-Pokémon canonical parties, unchanged original cores and intents, permanent holds after host loss, and three reconnected players waiting for the fourth. The fourth core had legitimately executed ADMIT but had not executed its first BIND. Its actual QUERY reported flags `129` (held and provisional), the original generation, four participants, local slot 3, phase 3 and ordinary sequence 0. The host already supported this state, but the client incorrectly required an unheld core with a different generation. The failed evidence remains preserved with SHA-256 `1338932f4aac487b748e91cd87ac71eb51315b81c6ba2bab3fcddc26e3cf2f37`; original sources were unchanged and all disposable proof cores closed.

The client now permits that exact provisional observation when its generation, participant count, local slot and mode match the original binding and its sequence proves the original BIND remains unexecuted. The immutable BIND comparison and nondecreasing lease/original-roster validation remain required. An ordinary held battle, foreign generation or participant, changed BIND, missing observation or consumed sequence still refuses recovery. This correction changes no native ABI, save bytes, dependencies or gameplay rules.

The affected Windows client cohort passed **23/23 methods in 12.746 seconds**, without skips. The two added regressions include refusal boundaries and the complete synthetic-native QUERY/BIND/SUSPEND/REAUTHORIZE/RESUME/RELEASE/RETIRE path over real authenticated loopback and binary IPC. These tests establish the client correction; actual-core qualification is recorded separately in [the interruption proof record](native-battle-resume-proof.md).
