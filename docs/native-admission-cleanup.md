## Exact boundary

An explicit **Cancel battle entry** action can revoke an original, fully consented entry only before the host has created any reservation row or published any route BIND. It accepts the exact original `BattleAdmissionIntent`, native incarnation, runtime UUID, generation, participant slot, original lease and unchanged canonical checkpoint. It never invents a battle result or uses ordinary RELEASE/ABORT to clear an unknown state.

`BattleAdmissionHost.cancel_admission` in `src/emerald_multiplayer/battle_admission_host.py` validates the actor's current authentication and exact successful native readiness receipt, then synchronously checks the durable consent, all reservation rows (including terminal rows), route-file absence, strict execution-file identity, pending/acknowledged commands and desk execution state. A waiting room with ready participants is permitted only when no reservation, BIND or prepared/started state exists. Before returning permission, it fsyncs an immutable canceled consent tombstone. Its digest includes that original consent; late capture/claim/prove cannot change canceled consent. Other original participants can obtain the same digest and clean up independently. `_reservation`, server `authorize_bind`, and executor exchange/first-command publication all recheck cancellation, including after restart.

`src/emerald_multiplayer/battle_admission_cleanup.py` owns typed readiness, cleanup and handoff authority. `Companion.battle_rpc` in `companion.py` refuses opcodes 22â€“24 without their exact typed authority, even when no other pending battle owns the core. Readiness is observational and can run while the exact original menu task owns the save lock. The launcher revokes consent **before** canceling/draining that captured task; only then can native HOLD run. A readiness refusal leaves the existing task and paused autosave loop intact. An uncertain host reply never means consent was safely revoked or that field play may resume.

The native boundary accepts either the genuine Enter menu latch or exact ADMIT state with unchanged party bytes/count and save counter. It rejects full BIND, prepared/started or indeterminate matches. Stale-party PREPARE refusal after BIND remains an outstanding cleanup problem under existing all-trainers recovery; this slice does not solve it. Host loss by itself never requests cancellation, introduces a forfeit, changes the roster, or relaxes the wait-for-everyone policy.

## Optional ABI and capacity

`gMultiplayerBattleAdmissionCleanupAbiVersion = 1` is advertised only by a matching verified compiler symbol. Manifest/config defaults remain zero when absent. Prerequisites are battle ABI 3, resume ABI 1, execution ABI 1, Players menu ABI 2 and emergency-save ABI 2. Save-window ABI is optional. Existing mailbox/control sizes and maximum native state 10 remain unchanged. Root capability checks live in `battle_manifest.py`, `bridge_config.py`, `companion.py`, `scripts/multiplayer/generate_manifest.py` and `bridge/mgba.lua`.

| Opcode | Payload and successful receipt | Purpose |
| --- | --- | --- |
| 24 `ADMISSION_CANCEL_READY` | 52 bytes: generation UUID, player UUID, runtime UUID, original lease u32 | Read-only exact-phase/capacity proof required by the host before cancellation. |
| 22 `ADMISSION_CANCEL_HOLD` | Same 52 bytes plus nonzero tombstone SHA-256 (84 bytes) | Replace the original provisional hold with a terminal callback/clock hold. |
| 23 `ADMISSION_CANCEL_HANDOFF` | Exact same 84 bytes | Release that terminal hold only after a fresh saver owns the current authenticated native save binding. |

All three controls use sequence 1 outside ordinary command sequencing, a nonzero battle UUID, exact incarnation/slot, singles or multi phase and current authenticated lease at least the original lease. Success echoes the exact payload; errors are empty. HOLD leaves native state IDLE with separate hold flag `0x20` and QUERY flags `1025`. It preserves party, RNG, save counter and the prior ordinary sequence. Exact retries are inert. Old ADMIT/BIND identities remain refused after handoff; late HOLD/HANDOFF cannot relatch or release a subsequent valid battle.

The native core retains **32 cancellation identities**, requiring 512 bytes for UUID tombstones plus a 240-byte last cleanup control, count/flags and alignment: the measured normal EWRAM increase is 756 bytes. Entries are never evicted, and production `MultiplayerBattle_Init` does not clear them. After 32 cancellations, marked Enter is refused **before** latching or publishing CHOOSE, showing `Entry limit: save and rejoin`; B/Close and normal saving remain available. A normal saved close and rejoin creates a new core lifecycle. No automatic reset, silent eviction or forced game restart occurs. READY still refuses a new cancellation at capacity before the host can irreversibly revoke consent; an already-held exact cleanup remains retryable at capacity. A preexisting unrevoked admission can continue to ordinary BIND after refusal.

Native changes are in `src/multiplayer_battle.c`, `src/multiplayer_menu.c`, `src/multiplayer_save.c` and `include/multiplayer_battle.h` in the engine delta below. The save guard allows exact successor arm/observation and emergency preservation while cleanup-held. Ordinary export/import/trade and cancellation remain blocked. Legacy READ is allowed only during an active emergency stream, so missing optional window support cannot prevent preservation.

## Interrupted lifecycle routes

1. **Before the host tombstone:** READY does not mutate consent or native admission. A refusal leaves ordinary progression possible. An unknown host result keeps the original held state and evidence; it is not a cancellation success.
2. **After the host tombstone, before HOLD receipt:** the original pending intent remains. The same original controller may replay only the exact already-persisted host-authorized HOLD after host loss. It cannot invent a cancellation, renew a lease offline, serialize the interrupted admission or discard a pending emergency candidate. Corrupt/uncertain evidence falls back to the original binding's permanent native emergency freeze without claiming a verified hold or safe close.
3. **After HOLD and host acknowledgment, before fresh saver arm:** the pending intent is archived and retired. A renewed authenticated lease can retry on the same original core. Immutable prior terminal records anchor renewal if pending intent unlink already occurred. If the old saver was already retired, its exact retirement receipt is checked against its archived predecessor and remains byte-for-byte unchanged. No pending intent is recreated.
4. **After fresh saver arm, before/after an uncertain HANDOFF receipt:** same-lease exact HANDOFF retry is supported. A subsequent host loss belongs to the newly registered emergency saver: it preserves a verified Flash candidate and permits normal close followed by cold reconciliation/fresh Continue. Pending emergency/export files prevent another cleanup or cross-lease handoff. The launcher requires that exact original retained core, cleanup intent, successor and successful completed preservation task before permitting close. Old handoff evidence is retained, not rebased into new authority. `tests/test_admission_cleanup_emergency.py` exercises real save-controller/SQLite/Flash recovery with the post-arm flag supplied by a fixture; actual native preservation at this cut remains separate qualification.

`EmergencySaveController.retire_after_admission_cleanup`, `prepare_cleanup_successor`, `complete_cleanup_handoff`, and `LauncherSession._adopt_battle_completion(..., cleanup=True)` implement these transfers. `AdmissionCleanupCompletion` is deliberately distinct from `BattleCompletion`; no unchanged revision or canceled challenge can be passed off as a finished playable battle.

Retirement on the same authenticated lease preserves the exact already-known native save binding and command cursor. The successor still performs fresh canonical/ownership/grant checks and durable emergency arming; it must not issue a duplicate native BIND with a reset cursor. A renewed lease clears the old binding and requires a real new BIND. The same rule applies to verified ordinary battle completion. `tests/test_terminal_saver_handoff.py` composes real regular retirement and successor arming with exact terminal records, and `tests/test_admission_cleanup_emergency.py` does the same for cleanup. Neither accepts an unknown binding or manufactures ownership.
