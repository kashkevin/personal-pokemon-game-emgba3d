# Native trade menu integration

The delivery source connects the existing durable exact-record exchange to the in-game Players menu. A player opens **Trade Pokemon**, the recipient discovers its own authenticated pending proposal, and each trainer chooses from the frozen personal party. Review screens bind confirmation to the exact displayed two-offer fingerprint. A changed offer creates a new screen generation; old input cannot consent to it. B explicitly requests cancellation. Server expiry, cancellation or commitment is reconciled through the existing immutable trade journal and native readback before field play resumes.

This remains the development exact-record capability. It does not enable the currently excluded evolution, egg, mail, form or Gen 6 handler-friendship cases; the accepted complete trade behavior still requires the versioned effects work in [native-trade-effects.md](native-trade-effects.md). Species numbers and levels are the initial bounded UI labels, pending polished names and summary screens. UI availability is not full trade acceptance.

## Native ownership and reuse

The isolated source is based on `de4ef98a2e`, preserving the qualified ownership, Players menu and trade-preview foundations. Menu ABI2 retains the existing 512-byte allocation and adds an explicit trade-reopen flag. The ROM accepts it only after its own exact CLOSE request and only in a live, unexpired, completely exported trade hold. Ordinary field, partial import, disconnected, expired and battle states cannot be opened this way. A reopened menu publishes a new native OPEN request before receiving choices. Menu closure releases the window and field locks, then publishes CLOSE; the Python operation owner waits for that acknowledgment before preparation, import or battle execution.

The native save hold remains authoritative throughout consent. B while a held dialog waits for a response cannot resume field callbacks. Menu rendering, fonts, window allocation, input and field locks reuse the pinned engine implementation. Current maintained upstream [`trade.c`](https://github.com/rh-hideout/pokeemerald-expansion/blob/7b95be15d84a053948791ce91e5dec0b168947a5/src/trade.c) and [`menu.c`](https://github.com/rh-hideout/pokeemerald-expansion/blob/7b95be15d84a053948791ce91e5dec0b168947a5/src/menu.c), plus official [mGBA scripting documentation](https://mgba.io/docs/scripting.html), were inspected on October 8. Native link trading still owns unrelated link/save callbacks, so it cannot replace the authenticated atomic commit by direct invocation. Existing compatible community audits are recorded in [customization-and-reuse.md](customization-and-reuse.md); no additional third-party source, library or asset was imported here.

The launcher stops and drains autosave around the menu handoff, permits one live interaction owner, and advances its local revision only from the exact completed native trade receipt. Battle completion retains the accepted checkpoint revision. Uncertain results keep their journals and disable new saves. An interrupted unpreserved core or pending battle cannot be destroyed by ordinary launcher task cancellation; ownership is retained until the player closes the game window.

## Qualified menu slice and remaining limits

The first Windows menu/proposal focus passed 42 tests in 15.505 seconds. A broader Windows trade/menu/launcher focus passed 89 tests in 52.363 seconds. A later 46-case focus passed in 3.723 seconds, including retention, ABI2 dialog and emergency adoption. The latest 173-method Windows batch passed all 168 menu, launcher, save, reset and existing friendship cases; five new paired-friendship fixture methods failed because their two save banks had inconsistent trainer identities. After fixing only that fixture, those five methods passed separately in 5.167 seconds. The failed combined log remains retained; it is not labeled a full passing run. These are Python network/controller fixtures, separate from native gameplay acceptance.

Native source `a97ff5301b565d821a7817865048c430946c2e15` built with 233,436 bytes EWRAM, 28,376 bytes IWRAM and 26,782,260 bytes used ROM. Initial normal/focused builds emitted generated dependency clock-skew warnings and remain historical evidence. Completed normal and focused rechecks were warning-free; the focused Multiplayer group passed **96/96** cases. The exact ROM is `d4675f82d17fd45bc28e8f284517df7d11fefdcc917d64edb12d768f982486eb`, ELF `e0a563bf3970e8dd5de4f1a9bd286e07b8d6e056f68f4968e2ee170167ec1282`, manifest `648d2ef6fa94ea80857cce46ec87f114010c429ce3b5c896804bfe467c572a80`.

The two-actual-core `trade-menu-core-2` proof passed ordinary Continue/enrollment; opening a proposal through Players; recipient offer selection; independent explicit confirmation; paired canonical revision 3 and exact native party readback; a second trade canceled with B; then two fresh Continue cores retaining the exchanged parties and cancellation outcome. Global ownership remained conserved and disjoint, database integrity passed, and original private source hashes were unchanged. The corrected path first waits for native menu CLOSE, then calls the existing coordinator's cancellation/commit reconciliation. It does not weaken the ownership guard.
