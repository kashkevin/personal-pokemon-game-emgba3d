# Read-only frozen Flash window

The optional save-window capability accelerates a held export or import readback. It reuses the engine's existing 4,096-byte `gSaveDataBuffer`; it adds no EWRAM allocation and grants no additional external write destination. The original 512-byte save mailbox, ordinary 128-byte reads/writes, ownership profile, journal, server commit and final complete-stream CRC remain in place. Builds without the capability keep the original transfer path.

The compiler-derived manifest adds `save_window_abi_version=1`, `save_window_abi_address`, `save_window_address` and `save_window_size=4096`. Generation requires the exact ROM marker and one allocated native sector buffer. Runtime validation checks the actual marker, ROM hash, ownership/trade/save dependencies, alignment, EWRAM bounds, and nonoverlap with presence, save and optional battle mailboxes. This address is only a read window. The Lua bridge still writes exclusively to the existing bounded inbound command slots.

Save opcode **18 READ_WINDOW** has empty command data and the existing incarnation/lease/operation/sequence/revision fields. Its Flash offset must equal the current read cursor, be aligned to 4,096 and lie between zero and 126,976. C admits it only in EXPORTING or COMMITTED; it refuses staging, unbound/bound state and completed trade holds. The ROM reads one Flash sector into its buffer, advances the existing stream cursor/CRC once, and publishes a four-byte CRC32 response at the original offset. A byte-identical last request returns the same descriptor without advancing again while the buffer remains held. Replaying a window after watchdog release is refused. Stale, skipped, misaligned and conflicting requests cannot select another memory address or change the cursor.

The read-only window is stable because normal field callbacks and other save/trade/battle mutations are excluded during the hold. The Lua bridge first correlates the normal mailbox response, checks that it remains in EXPORTING/COMMITTED, copies exactly 4,096 bytes, checks the window CRC and rechecks response generation/state. It closes IPC on inconsistent readback. Import staging and Continue cannot expose this buffer through the new command.

The optional IPC capability is `X` plus little-endian `<HH>(1,4096)`. Successful window responses are `F` plus the usual 240-byte control and exactly 4,096 bytes. Error responses retain `R` with an empty control payload. The companion authenticates the ordinary loopback token before permitting the larger **4,337-byte** frame limit, and accepts `F` only after the verified capability. It validates the response's offset, UUID, lease, incarnation, sequence, revision, size, opcode and CRC before completing the request. No server frame limit or inbound Lua command limit is enlarged. Partial writes retain one bounded outbound frame; this does not authorize an unbounded queue.

`LiveCheckpointCoordinator._read_flash()` chooses 32 window requests only when both the verified manifest and connected bridge support them. Otherwise it uses 1,024 ordinary 128-byte READs. The complete image still passes the same Flash/ownership parser, immutable journal-before-upload ordering, exact canonical transaction and native END CRC. A read failure cannot publish an incomplete image as a checkpoint. Import writes remain 128 bytes; only their final full readback can use windows. This change does not itself enable periodic autosave, select an offline policy or promise a final save at window closure.

## Actual-core proof and measured limits

`scripts/multiplayer/save_window_proof.py` drives two official mGBA cores through ordinary joypad input and the production bridge/coordinator. Each run uses a fresh world and copies of immutable source saves. Both completed runs passed all 13 checks and closed all cores. They compare every exported Flash byte against read-only core diagnostics, verify held party/RNG/playtime and independently moving nonparticipants, refuse replay/offset/stale/CRC errors, retain the server head after corrupt readback, recover through the committed-import window, and perform an ordinary native save and fresh Continue with unchanged ownership identity. The first development run stopped at an incompletely acknowledged native save prompt; its failed evidence is retained.

| Run | Complete window checkpoint | Window read portion | Legacy checkpoint | Full recovery |
| --- | ---: | ---: | ---: | ---: |
| Unthrottled headless | 1.687 s | 1.081 s / 32 requests | 16.546 s | 18.140 s |
| Headless paced at 60 frames/s | 9.298 s | 4.592 s / 32 requests | 39.254 s | 47.768 s |

The paced run advances one official core frame per tick without catch-up. Its legacy read takes 34.549 seconds across 1,024 requests. These are complete lifecycle measurements on this development machine, not native Windows frontend qualification. The remaining roughly nine-second hold is still a delivery performance problem; periodic autosave stays disabled in the normal runtime. Import staging still performs the original 128-byte writes. Further optimization must preserve the same CRC, journal, canonical commit and release checks.

A separately frozen [CRC table optimization](save-performance.md) subsequently reduced the paced complete checkpoint to 6.328 seconds and the window read to 1.611 seconds, with all 13 actual-core checks passing again.
