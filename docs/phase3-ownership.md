# Phase 3: Pokémon ownership foundation

Status: verified ownership foundation, recorded by `OWNERSHIP_FOUNDATION_POC` in the project and engine repositories. This slice adds persistent instance identities, explicit enrollment, bounded allocation, and an atomic ownership ledger to the existing live checkpoint flow. Cross-player transfers and the Windows Host/Join package remain future milestones.

## Identity and scope

A Pokémon instance is identified by its world UUID and a nonzero 20-bit server-issued serial. Personality, original trainer, species, and slot are attributes rather than identity. Serial ranges are committed in SQLite before the ROM receives them, never recycled, and explicitly refuse exhaustion at 1,048,575 instances per world. Unused allocations remain burned after interrupted operations.

The inventory contains 432 possible slots: six party members, 420 PC slots, two Emerald daycare slots, and four fusion storage slots. Saved party copies, previous Flash banks, battle records, and temporary battle parties are not additional instances. The ROM validates the entire inventory before assigning IDs during a frozen export. Assignment consumes no gameplay RNG.

Boxed Pokémon remain 80 bytes and party Pokémon remain 100 bytes. The serial uses six spare fields inside the encrypted, checksummed substructures: 6 + 3 + 2 bits in substructure 0, 5 + 3 bits in substructure 1, and one bit in substructure 3. Ordinary structure copies preserve the ID. The separate Pokémon created by Shedinja's evolution path starts unassigned. Local egg hatching retains identity; traded eggs require a later audited origin-key update before trade support.

## Explicit enrollment

The ownership profile is `rhh-1.17.1-bb1093-ownership-v1`. Schema-1 worlds and legacy builds remain usable through their existing APIs; opening them never silently migrates them. The development enrollment path provisions a new schema-2 world and explicitly records a copied, validated legacy source through `OwnershipCheckpointStore.enroll_player`. The source's complete hash, bytes, trainer identity, and normalized inventory remain provenance. One identical source cannot enroll two players in that world.

The first owned checkpoint must preserve every source Pokémon's location and normalized boxed content. Only ID assignment and volatile party statistics may differ. Enroll before playing, moving Pokémon, gaining experience, or changing their boxed content. `LiveCheckpointCoordinator.enroll()` is explicit; an ordinary checkpoint refuses an unenrolled game. This does not establish a historical anti-cloning guarantee for saves made before identities existed. Migrating an established ownership world to another build must retain its world UUID and identities in a separately validated migration.

## Save record and commands

SaveBlock3 grows from 4 to 600 bytes, within its existing reserved sector chunks. The old four-byte prefix remains in place. The 596-byte ownership record begins at byte 4 and contains `EMO1`, version 1, record size 596, world/player/grant UUIDs, allocation start/end/next counters, lease and incarnation, and a 128-entry retirement journal. A CRC32 at byte 596 covers bytes 0–595, including the retained prefix. Existing engine sector checksums exclude these reserved chunks, so this additional CRC is required.

The allocated live-save mailbox remains 512 bytes. Opcode 10 queries an 80-byte ownership status. Opcode 11 supplies world/player/grant UUIDs, start, exclusive end, and an explicit enrollment flag in 60 bytes; its success response repeats the 80-byte status. The server issues bounded grants through the authenticated `ownership_grant` RPC. No Pokémon manifest is sent as an oversized JSON message: the server derives membership directly from the uploaded Flash.

Every load, import, native initialization, and new mailbox binding revokes volatile mint authority. Persisted counters alone never authorize allocating IDs after rollback. The companion obtains a fresh range before exporting again; existing Pokémon keep their IDs. A retry of the same active grant cannot rewind its cursor. Live recovery compares the complete canonical state before releasing the game, and receipts retain the exact canonical and native Flash hashes.

Enrolled games route the old partial save routines through a coherent full save. They refuse temporary-party serialization before changing IDs. The parser allows a valid previous ownership bank to contain newly acquired, unassigned Pokémon from an ordinary Save; the selected canonical checkpoint must contain IDs for all owned Pokémon. This distinction permits an ordinary Save followed by a checkpoint without treating the older bank as canonical ownership.

Native party compaction can leave the old maximum HP in an empty slot's 14-bit `hpLost` header field: `ZeroMonData` clears the Box data, then sets HP before maximum HP. The parser permits that sole residue in an otherwise zero empty Box, with no species, ID, checksum, or other header/secure data. It preserves the exact uploaded bytes and container hash. Occupied Pokémon retain HP bookkeeping in their content hash, and duplicate/retired identities and all other empty-slot corruption remain rejected.

## Mutation and transaction rules

The true PC release path records retirement only after the game's release checks succeed and before deleting the Pokémon. A full journal refuses deletion. The game's temporary “released” message during a failed HM release is not retirement. The ROM clears acknowledged retirement entries from RAM only after the durable checkpoint acknowledgment; saved entries can safely repeat after a crash or recovery.

Assigned Pokémon also require a verified checkpoint acknowledgment after loading or an interrupted export before they can be released. This prevents an export interrupted before local journaling from producing retirement entries for IDs the server never registered. Newly acquired Pokémon whose ID is still zero can be released normally; they have never entered canonical ownership.

The server commits the checkpoint, latest revision, membership, ownership events, and permanent retirement records in one SQLite transaction. It rejects duplicate, unknown, foreign, or retired identities, changed origin attributes, and disappearance without an explicit retirement entry. Historical exact retries return their original result without replaying ownership changes. Ordinary checkpoints never transfer ownership between players.

An uncommitted pending export can retry its unchanged bytes, original base revision, and transaction UUID after reconnecting. The current authenticated network lease supplies authority; the lease and incarnation embedded in the save identify the original allocation grant. A stale network connection cannot commit. Pending recovery never rewrites the save to pretend it was produced under a newer grant.

An identity becomes canonical at its first accepted checkpoint. A legitimate Pokémon already assigned before a reload may carry an ID from an older range issued to the same player. The server therefore permits first-seen IDs from that player's burned ranges, while the trusted ROM enforces that old grants cannot mint again. This foundation does not claim protection against a modified client forging unused IDs or arbitrary gameplay attributes. Registered identities cannot duplicate, change owner through an ordinary save, or resurrect after retirement.

Frontier, rental, and other temporary-party modes are outside this ownership slice. Enrolled games refuse native NPC, cable, Union Room, and spin-trade admission before mutation until their transaction hooks are implemented; legacy unenrolled games retain their existing behavior. Automatic checkpoint scheduling, disconnected-play policy, cross-player trades, battles, teams, and Local Soft Reset remain later work in the accepted phase order.

Storage tests exercise allocation durability, exact retries, atomic failures, foreign ownership, tombstones, restart, and schema separation. These synthetic tests are distinct from actual ROM gameplay evidence.
