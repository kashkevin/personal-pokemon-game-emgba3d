# Pokémon Emerald private multiplayer

This project targets a private adventure for one to four players total using Emerald as its foundation, with independent exploration and saves, Gen 1–6 Pokémon, Gen 6 mechanics including Fairy, 18 starters, and all eligible officially released Mega Evolutions, including later additions.

Current checkpoint: **four actual clients, recoverable paired trades, and a bundled native Windows runtime.** Four Emerald cores passed 30 checks covering remote players, independent maps/menus/encounters, disconnect/rejoin, individual checkpoints and fresh Continue. Two-core trade proofs cover exchange, lost confirmation/server restart, one-sided preparation cancellation, and closed-game recovery before Continue. The Windows runtime has loaded the correct owned character through the verified startup/save-lock lifecycle. [Four-client evidence](docs/four-player-foundation.md), [trade evidence and limits](docs/trade-foundation.md), [Windows runtime](docs/windows-runtime.md).

The latest combined Python regressions passed **518 tests on Windows and 520 on WSL, without skips**; a subsequent 43-test battle lifecycle/validator group also passed on Windows. The frozen diagnostic-channel ROM passes 5,443 engine tests, retaining the baseline's 18 known failures, 421 TODOs and nine expected failures. Two actual cores have exercised typed native message exchange and reconnect recovery; **native 1v1 and full-six-per-trainer 2v2 are still being implemented**. [Diagnostic contract and proof](docs/battle-channel-mailbox.md), [native battle implementation contract](docs/native-singles-prototype.md), [consent/lifecycle service](docs/native-battle-desk.md).

An opt-in [autosave scheduler](docs/autosave-foundation.md) now handles safe admission, session changes and uncertain saves. Its [read-only save window](docs/save-window.md) and verified CRC optimization reduced a paced checkpoint from 39.254 to **6.328 seconds**; ordinary native saving accounts for most remaining delay. Automatic scheduling stays disabled in the normal runtime pending further [performance and Windows qualification](docs/save-performance.md). Pinned TLS and [host/account invitation provisioning](docs/host-provisioning.md) are implemented separately. Local encounter Soft Reset, native trade effects and player menus, the Host/Join interface, import/patch packaging, and separate-PC LAN/Internet acceptance remain required before this becomes a friend-ready download. These foundations do not claim the full content backlog is complete.

Read [the master specification](docs/master-spec.md) for accepted gameplay, [the current delivery roadmap](docs/development-roadmap.md) for the owner's latest priority order, [the technical foundation](docs/technical-foundation.md) for architecture, and [the Gen 6 audit](docs/gen6-foundation-update.md) for ruleset requirements and Mega adaptations. The next sequence is safe trading → battles/teams → four-player proof → local encounter Soft Reset → automatic saves/disconnect handling → Windows Host/Join → Wi-Fi/Internet polish. Existing content requirements remain in scope.

The [combined amendment](docs/project-update-customization-friendship-shiny-charm.txt) adds synchronized Trainer customization, research/reuse before major systems, pair-specific friendship and Lucky trading, and a personal Shiny Charm with guaranteed Game Corner redemption. These are specified future features; [reuse research and customization architecture](docs/customization-and-reuse.md) guide their implementation after the required multiplayer foundations. Original briefs and all amendments remain preserved verbatim.

The requested delivery is a downloadable Windows game with **Host Game / Join Game**, for four players total including the host. The owner's PC hosts over home Wi-Fi, with direct Internet connections through port forwarding. Friends should need no compiler, Python installation, VPN, or manual emulator script setup. [Local PC setup](docs/local-pc-setup.md) records the packaging target, hosting setup, and development downloads. The bundled runtime is tested; the complete player package remains in development.

The baseline is RHH `pokeemerald-expansion` at `expansion/1.17.1`, commit `bb1093a7c72d3961d9a37d8e02ad2abc2c866682`, built in Ubuntu 24.04 under WSL2. The [build record](docs/baseline-build.md) records versions, artifacts, and acceptance status; the [dependency ledger](docs/dependency-ledger.md) records provenance. The Lua bridge, companion, allocated ROM mailboxes, remote-avatar adapter, durable storage, live checkpoints and ownership are implemented. Trade recovery is verified; native trade effects and the player interface still require integration and actual-game acceptance.

Development must preserve small commits, repeatable tests, and known-good checkpoints. `RESEARCH_FOUNDATION_V1` records documentation only. The engine's `BASELINE_BUILD` preserves the accepted unchanged source, `MULTIPLAYER_POC` records local movement, and `DURABLE_CHECKPOINT_POC` records closed-game save recovery. `LIVE_CHECKPOINT_POC` records live save/recovery, and `OWNERSHIP_FOUNDATION_POC` records the verified ownership slice in both repositories. Private build artifacts and save evidence remain archived.

ROMs, player saves, server databases, and private backups are excluded from Git. No ROM download or distribution is part of this repository.
