# Pokémon Emerald private multiplayer

This project targets a private adventure for one to four players total using Emerald as its foundation, with independent exploration and saves, Gen 1–6 Pokémon, Gen 6 mechanics including Fairy, 18 starters, and all eligible officially released Mega Evolutions, including later additions.

Current checkpoint: **four actual clients, 2v2 battles with six Pokémon per trainer, recoverable paired trades, and a bundled native Windows runtime.** Four Emerald cores passed 30 exploration/lifecycle checks; the later full-party battle proof passed exact personal restoration, independent saves and fresh Continue for all four players. Two-core trade proofs cover exchange, lost confirmation/server restart, one-sided preparation cancellation, and closed-game recovery before Continue. The existing Windows runtime has loaded the correct owned character through the verified startup/save-lock lifecycle; the latest combined battle/reset build still needs Windows qualification. [Four-client evidence](docs/four-player-foundation.md), [trade evidence and limits](docs/trade-foundation.md), [Windows runtime](docs/windows-runtime.md).

The latest complete Python regressions passed **604 tests on Windows and 616 on WSL, without skips**. The Windows run preceded twelve new 2v2 consent/arbitration cases; those passed in a subsequent **82-test affected group on both systems**, and the WSL full run includes them. The service requires each of four trainers to consent separately and reserves all four characters until every required abort or release acknowledgment arrives. Durable interruption and result policies remain pending. [Consent/lifecycle service](docs/native-battle-desk.md), [server arbitration](docs/native-battle-arbitration.md), [transport and regression record](docs/native-battle-transport.md), [durable admission guard](docs/native-battle-admission.md).

The combined native battle/reset source passes **70 focused tests and 5,484 complete-suite tests with zero unexpected failures**, retaining 18 known failures, 421 TODOs and nine expected failures. Four actual cores completed a 2v2 with **six occupied Pokémon per trainer**; three trainers switched through their sixth Pokémon while the fourth kept its starter. All four recovered their exact original parties and personal RNG, saved independently and passed fresh Continue. Earlier native 1v1 and four-core observer proofs remain recorded separately. The opening VS preview still shows three Pokémon per trainer; broader battle effects, durable recovery and player menus remain required. [Native singles proof](docs/native-singles-proof.md), [full-party Multi proof and limits](docs/native-full-multi.md).

An opt-in [autosave scheduler](docs/autosave-foundation.md) handles safe admission, session changes and uncertain saves. Its [read-only save window](docs/save-window.md) and verified CRC optimization reduced a paced checkpoint from 39.254 to **6.328 seconds**; ordinary native saving accounts for most remaining delay. Automatic scheduling stays disabled in the normal runtime pending further [performance and Windows qualification](docs/save-performance.md). Pinned TLS and [host/account invitation provisioning](docs/host-provisioning.md) are implemented separately. On the same combined ROM as the full-party battle proof, the default-off [local reset test encounter](docs/local-soft-reset-design.md) passed **21 four-core checks** using the guarded Select prompt, cancellation, a fresh roll, ordinary capture, saving/recovery and fresh Continue while three other players remained independent. These separate runs do not complete simultaneous battle/trade/reset coverage. Production reset encounters and Windows input, native trade effects and player menus, the Host/Join interface, import/patch packaging, and separate-PC LAN/Internet acceptance remain required before this becomes a friend-ready download. These foundations do not claim the full content backlog is complete.

The requested delivery is a downloadable Windows game with **Host Game / Join Game**, for four players total including the host. The owner's PC hosts over home Wi-Fi, with direct Internet connections through port forwarding. Friends should need no compiler, Python installation, VPN, or manual emulator script setup. [Local PC setup](docs/local-pc-setup.md) records the packaging target, hosting setup, and development downloads. The [Host/Join session backend](docs/launcher-session.md) reuses authenticated TLS, installation pins and the protected runtime lifecycle. Existing characters can recover committed trades while new trades remain disabled; **91 affected tests passed on Windows and WSL without skips**. The visible interface, first-character enrollment, updated combined runtime bundle and complete player package remain in development.

The baseline is RHH `pokeemerald-expansion` at `expansion/1.17.1`, commit `bb1093a7c72d3961d9a37d8e02ad2abc2c866682`, built in Ubuntu 24.04 under WSL2. The [build record](docs/baseline-build.md) records versions, artifacts, and acceptance status; the [dependency ledger](docs/dependency-ledger.md) records provenance. The Lua bridge, companion, allocated ROM mailboxes, remote-avatar adapter, durable storage, live checkpoints and ownership are implemented. Trade recovery is verified; native trade effects and the player interface still require integration and actual-game acceptance.

Development must preserve small commits, repeatable tests, and known-good checkpoints. `RESEARCH_FOUNDATION_V1` records documentation only. The engine's `BASELINE_BUILD` preserves the accepted unchanged source, `MULTIPLAYER_POC` records local movement, and `DURABLE_CHECKPOINT_POC` records closed-game save recovery. `LIVE_CHECKPOINT_POC` records live save/recovery, and `OWNERSHIP_FOUNDATION_POC` records the verified ownership slice in both repositories. `NATIVE_SINGLES_POC` records the qualified native battle slice and its explicit limits. ROMs, player saves, server databases, and private backups are excluded from Git. No ROM download or distribution is part of this repository.
