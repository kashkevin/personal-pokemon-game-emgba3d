# Known issues

Confirmed problems only. Severity: Blocker / High / Medium / Low.

## Native multiplayer (Milestone C, engine `src/platform/mp_bridge.c`)

| ID | Severity | Issue | Reproduction | Status |
| --- | --- | --- | --- | --- |
| M1 | Medium | The companion verifies a GBA ROM and its manifest, never the native executable: a native client is paired with the ROM built from the same engine source by whoever starts it. A mismatched pair would show up only as a capability or mailbox refusal, not as an identity error. | Start a native client next to a companion given another build's ROM. | Mitigated for games the launcher starts: a native runtime bundle names the ROM build it was made with and the launcher refuses another before recovery or start (app `player_runtime.py`, run native-launcher-4). Open for a native game started by hand; before release: embed the build id in the executable and have the bridge report it, or give the companion a native manifest. |
| M2 | Low | Exercised natively so far: presence (connect, see each other, movement), a map change through a door, a companion restart while the game runs, and live checkpoints into the ownership store (enrollment, save after walking, game restart, save again, live recovery into a running game). Trades, battles, the Players menu, Local Soft Reset, autosave/emergency save and shared-world actions go through the same ported code (unit-tested) but have not run natively. | - | Open: next native proofs (trade, 1v1/2v2, Players menu). |
| M4 | High | The bridge fell behind when the native game ran slowly. mgba.lua's per-frame budgets (1 KiB received, one frame sent, a pose every 6 frames) assume mGBA's constant 60 frames a second; the native game slows down with its drawing. Two 3D clients on software OpenGL ran at 2.4 frames a second: the companion's snapshots (10 a second) backed up in the socket, save commands waited 6-12 s behind them and enrollment timed out; a pose every 6 frames (2.5 s) also reads as a paused game to the companion (0.5 s), which would hold autosave. | `native_checkpoint_proof.py` with two 3D clients outdoors, engine before `edb755a26` (run native-checkpoint-3d-1; diagnostic diag-3d-save-2). | Fixed (engine `edb755a26`): per game frame up to 16 KiB received and 8 frames sent; pose and shared-world record every 100 ms of real time. Verified: the same 3D run passes (native-checkpoint-3d-3), 2D and Wine runs still pass. |
| M5 | Low | A live save holds the game from export to release for about 34 bridge round trips of 2 game frames each: about 1.1 s at 60 frames a second (the emulator build pauses about 6.3 s, roadmap 5.7). The frames were paced by drawing, so the 3D build at 2.4 frames a second (software OpenGL) took 32-38 s per save. Fixed for the hold (graphics `2f150c4db`): while the save holds the game and no menu is open the frames run at 60 a second without being drawn (redrawn once a second); the same run now takes 4-6.5 s per save, the rest being the few commands before and after the hold, which still run at the drawing rate. A live recovery (or a trade's import) is 1024 more round trips: 37 s at 60 frames a second, 69 s in the 3D build on the cloud computer with the fix. | `native_checkpoint_proof.py` with two 3D clients (runs native-checkpoint-3d-4 before, -3d-5 after). | Fixed for the hold; open for long imports: answering several save commands per frame would shorten recoveries and trades in every build (not started). |
| M3 | Info | Test environment only: two Windows clients under Wine that share one prefix lose keyboard input (one wineserver, one foreground window), so key presses to one of them are dropped. The proof gives each client its own prefix. | `scripts/multiplayer/native_presence_proof.py --wine P --wine P`. | Not a game issue; documented in TEST_PLAN. |

## Diorama 3D renderer (branch `claude/native-graphics`, `DIORAMA=1` build)

| ID | Severity | Issue | Reproduction | Status |
| --- | --- | --- | --- | --- |
| V1 | Low | The follower Pokémon is not drawn in 3D while its sprite uses affine scaling (coming out of or going into its Poké Ball) or a multi-part subsprite table; the renderer refuses those sprites (the classic 2D view draws them). | Heal at a Pokémon Center, then walk; with `PKMN_DIORAMA_LOG=1` the log shows `object local 254 ... refused (unsupported sprite)`. | Fixed (graphics `8dda1e1be`): affine sprites are drawn transformed by their matrix, and the follower's Poke Ball phase (a 16x32 single-part subsprite table) is accepted, so the follower comes out of and goes into its ball in 3D with no cut to 2D. Multi-part subsprite tables (a walker half hidden in tall grass) are still refused. |
| V2 | Info | The voxel project's own rule test `test_rules_parity.py` fails: the C classifier gives height 32 where the Python model gives 0 (layout 1, cell 0, metatile 468). The same test fails the same way in the voxel project's tree at `cfb429bd1`, so it is upstream, not caused by the port. | `python3 tools/diorama_rules/test_rules_parity.py` | Open (upstream); investigate before relying on that record. |
| V3 | Info | Outdoor 3D scenes are heavy for software OpenGL: Route 101 is about 746,000 triangles per frame (mostly voxel trees). In the cloud workspace (Mesa llvmpipe, 2 CPU cores) that is 3-6 frames per second; all sampled time is inside Mesa. Below 12 fps the game slows down with the renderer (frame clamp in `sdl2.c`, by design). With modelled buildings and sun shadows (engine `65f44c42e`), Oldale Town by day standing still: 7.1 fps (7.6 with `PKMN_DIORAMA_SHADOWS=0`; 3.4 before the shadow map was kept between frames); the Oldale Pokémon Center about 44 fps. | `PKMN_PERF_LOG=1`, walk on Route 101 or stand in Oldale Town. | Not a bug in itself. Frame rate on a real GPU is **unmeasured** (owner's PC test, `run-3d-perf.bat`). Tree instancing/LOD only if a real GPU needs it. |
| V4 | Info | The voxel project's rule-compiler test `test_repository_mountains_are_one_block_art_masked_cliffs` fails: some mountain records carry measured flag 128 as well as 32. Same failure in the voxel project's tree at `cfb429bd1` (22 of 23 tests pass in both), so upstream, not caused by the port. | `python3 tools/diorama_rules/test_compile_rules.py` (about 9 min, 3.3 GB RAM) | Open (upstream); check when cliff art looks wrong. |
| V5 | Low | At night the Diorama's 3D tree crowns stay noticeably brighter than the same trees in the classic 2D view's night tint (ground and buildings match). The trees come from the Diorama's own tree path, which the D4 work did not change (its shadows only darken). | Play after 20:00 game time, press F4 to compare. | Fixed (graphics `398d486ef`): the voxel tree model's colours were baked; they now follow a per-channel line fitted each frame from the trees' palette, so night tint and fades reach them (identity by day). | V6 | Low | Doors on modelled buildings do not open in 3D: the game animates the door on the tilemap, which the 3D view does not show, so the player walks into a closed door before the warp (the 3DS project draws a black opening on the wall). | Enter any house from the 3D view. | Fixed for modelled buildings (graphics `398d486ef`, the 3DS project's door ported): a black opening widens and narrows with the door and a walker going through darkens and is gone.
