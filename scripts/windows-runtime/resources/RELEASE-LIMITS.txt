Emerald Together — private release limits

This guide accompanies private packages for up to four players. README.txt and
_internal/package-provenance.json identify the exact frozen package and whether
Import my game is available. A source change or a successful package build is
not evidence that its gameplay, installation or network paths have passed.
Earlier private package 7 remains unchanged and import-disabled. Testing resumed
on October 9; later isolated worker, ROM and BPS reconstruction checks have their
own evidence. They do not qualify a new player package. Earlier acceptance
belongs only to its recorded frozen pins.

Current release source

A package labeled "Gen6 defaults" has a separately identified ROM and ruleset.
Its compiled descriptor verifies eighteen selected generation defaults against
the exact game bytes. This does not complete the 721-species acquisition gates,
TM/tutor/egg data, all forms/Megas, or every generation-dependent mechanic.
Later species remain compiled to preserve the existing save layout; that is
not permission to use them in the intended Gen1-6 game. Separate affection and
friendship, explicit later-mechanic booleans and full content eligibility still
need work. Existing Pokemon and learned moves are not rewritten. Shiny odds
were not changed. Keep candidate 9 for its existing worlds; there is no world
migration or repinning path to this candidate.

Normal packaging requires a pinned installation patch, the full 25-source
production Local Soft Reset descriptor, and a compatible ROM-declared native
trade replay entry point with its separately pinned Windows worker. It also
requires a compiled player-build descriptor, checked against the exact ROM,
that disables the overworld debug menu, battle debug menu, Pokemon sprite
visualizer and debug trainer-ID suppression. Candidate 10 predates this gate
and is preserved as a blocked diagnostic package; do not share it for play.
A private development preview is explicitly marked and may omit release gates.
The importer accepts the matching owner-supplied raw GBA dump or one valid GBA
inside a bounded ZIP. It never downloads a game or changes the original dump.

Production reset source now enables the 25 authored personal adapters with
development/test modes off. Compiled adapter availability does not establish
current encounter eligibility: tickets, progression, watering, event exclusions,
object identity and first-action guards remain in force. Ordinary wild battles
and world events are excluded. The capability-gated classic reset chord requests
Local Soft Reset only; unsupported or unsafe contexts suppress emulator reboot.
Attempt records count durable pre-generation admissions, not shiny encounters,
captures or altered probabilities. Complete encounter-by-encounter gameplay
qualification of these latest adapters remains incomplete.

Native recipient trade-effect source now connects explicit move decisions,
recipient save candidates, host replay and atomic paired effect/history storage
under the world's explicitly chosen Gen 6 handler rule. The host worker uses a
fresh isolated core and original canonical checkpoints; it cannot access a live
player core. Unsupported records, including eggs/mail in this adapter, remain
refused. Its Gen 6 move limits also reject later-generation moves such as
Leafage; an existing Pokemon with an unsupported move cannot use this flow.
How imported later-generation moves should be handled remains an owner decision;
this candidate does not delete, substitute or silently permit those moves.
The isolated Windows worker and copied native record/save-block replay
have passed scoped checks. Those checks do not qualify the complete visible
trading experience or recovery in a new Windows package.

Main menu, Host Server / Join Server and characters

The program opens on the main menu inside the game's own window (Continue Adventure, New Game, Host Server, Join Server,
Settings, Exit). It is a front end: starting a game, the checks before it, hosting, joining, saving and recovery are the same
code as before. A friend joins with an invite code (a password for that account: give each friend only their own) or an
invitation file; there is no relay server, no automatic discovery, no UPnP and no NAT traversal. Internet hosting still
needs the host's own router port forward and firewall rule. First-time characters are created with the game's normal New
Game and registered automatically (a friend's with the host's server over the world connection; the host can turn that off).
The menu is mouse and keyboard; a controller's D-pad, A and B are handled but untested. It was checked by automated tests
and screenshots on a simulated display and, in CI, on a Windows runner without a graphics card; a real-PC walk-through of
every menu path, the real New Game and enrollment sequence, and a real LAN or Internet join are still pending. The menu
window and the game are two windows of the same program; the earlier launcher window is a fallback
("EmeraldTogether.exe --classic-launcher").

The program provides local world creation, named character accounts, separate friend invites and one-time own-game
import when the package includes its verified patch. A character still starts as the game's ordinary New Game (name,
starter, native Save) and is enrolled by the unchanged first-enrollment path: the host's own PC approves the host's
character; a friend's source is sent over the world connection and the host's server checks and records it for the
authenticated account (it must be a valid new save with no owner identities, not another account's source; the host can
turn this off per world). That is not a registration of strangers: only an account with its own invite can do it. An
existing world can use the explicit, backed-up feature upgrade only with its original game identity; setup cannot repin
it to another release. Keep each friend's invite private and separate from the shared application ZIP. The earlier
file-export path (a friend exports a verified unassigned .sav for the host to approve) remains in the fallback launcher
window. Changed, owned and invalid sources are refused, and existing destinations are never replaced.

Saving and recovery

Autosave defaults on and waits five minutes plus a safe field opportunity.
Its toggle is remembered for this character and world on this PC. Save now
also works with autosave off. Both normally need a reachable host. The game's
own Save menu and window closure do not confirm a canonical host checkpoint.
Wait for the launcher's successful save message before ordinary closure.

Host loss can preserve a safe field save or finish an ordinary save already in
progress for later reconciliation. Unsafe or uncertain operations may remain
held without a completed save. Preserve private recovery files and keep the
original game open whenever the launcher says recovery is needed.

Resolve interrupted trade is an explicit recovery action after the host
returns. It uses authenticated retained evidence to cancel unfinished work or
retain a committed result. Only the verified close-ready message permits
normal game closure followed by the same identity's Host/Join cold recovery.
Unknown evidence remains held. This is not same-core resumed trading or whole-PC
reconstruction; each original surviving player follows their own recovery status.

Interrupted multiplayer battles wait for every original participant and retain
their original games. Recover battle and Restart host service do not recreate
an exited core, application or PC, and do not permit a replacement player.
Cancel battle entry is limited to an authenticated, never-reserved entry with
affirmative native handoff evidence; it does not cancel a started match.
An invitation, consent, result record or receipt alone does not prove the whole
battle, save, fresh Continue or interrupted recovery path passed.

Verification boundaries

Recorded earlier Windows scenarios cover specific real Host/Join, timed autosave,
manual saves, pre-entry cancellation, native 1v1 and native 2v2 flows with their
own pinned source, runtime, input parties and normal-close evidence. They do not
retroactively qualify later unbuilt source or a newly packaged executable.

Candidate 9's actual GUI BPS import passed in a fresh private profile using the
owner's supplied ZIP; that ROM and package remained unchanged. This does not
qualify a different candidate's setup, gameplay or whole installation flow.
Clean-machine installation, physical keyboard,
audio, gamepads, four separate Windows PCs, Wi-Fi and outside-network Internet
gameplay remain separate acceptance gates. Ordinary desktop key automation did
not establish physical keyboard failure. Check connection verifies the invited
TLS endpoint only; it sends no character login and proves no Internet gameplay.
The application does not alter firewall rules or configure router forwarding.

The download must contain no game ROM, player save, world database, private key
or invitation. Component pins, notices and covered native source/relink material
remain under _internal. Those materials and patch packaging do not by themselves
resolve game-content distribution permissions. Campaign, region, customization
and remaining master-specification work are not declared complete here.
